# v0.13 — a broken contract is a conversation, not a crash

## Goal

On 2026-08-28 at `06:24:03Z`, a run called `deck-phase3g` ended like this:

```
state:     aborted
verdict:   unverified
reason:    'worker' contract violation: $.task_id: expected string, got int
phase:     None  approach 2/12
iteration: 135/900
tasks:     3/13 completed (1 in-progress, 9 pending)
usage:     ~$174.52 derived, 311755k tokens
```

The worker had written `{"verdict": "complete", "task_id": 104}`. `104`, not `"104"`. Its
own sentence immediately above that line: *"Task 104's success criteria are met: all sites
converged, evidence quoted and committed, `clientOpensCreateModalForAgent` converted, proof
scenario added, and the targeted validation run exits 0 with the log stored."* The work was
done. The harness threw away **765 iterations**, **10 of 12 approaches** and **~33 hours**
of remaining wall clock — after 14h 36m and ~$174.52 — because a JSON scalar was unquoted.

This wave is about the harness's own manners. A hat that breaks its output contract is
told, precisely, what it broke, and asked again. It is not executed.

The machinery for that already exists in this repository, complete and unit-tested, and is
connected to nothing but the planner. Half 1 finishes the cutover the code's own comments
have been promising since v0.9 (#92). Half 2 makes an iteration able to say why it failed,
which today only the *last* failing iteration can (#89). Half 3 moves the plan-building
practices every recent wave had to spell out by hand into the planner prompt itself (#90).

Four issues: **#92** (the wave's centre), **#89**, **#90**, and **#93** — a regression on
`main` at launch which, left alone, would make this wave's own final sweep a false green.

## Read this before anything else

1. **This wave edits `loop.py`, the most dangerous file in the repository.** Five call
   sites, in the supervisor that drives every run including your own. A mistake here does
   not fail a test, it ends runs. Every change to `loop.py` in this wave needs a test that
   fails without it — no exceptions, and no "covered by the sweep".
2. **You are not being asked to invent the mechanism.**
   `src/ralphd/engine/contract_enforcement.py` is finished work: `enforce_contract`
   re-prompts with the specific validation error up to `contract_retry_max` times, emits
   `contract.violation` per failed attempt and `contract.agent_fault` once on giving up,
   and hands back `ContractResult(ok, payload, attempts, agent_fault, errors)`. Read it and
   `tests/test_task_status_lifecycle.py:200-260` (which drives it end to end against a
   synthetic hat) before designing anything.
3. **The fault cause is not lost — it is simply never derived per iteration.** See
   requirement H. Do not build a persistence layer for something already on disk. #89's
   own first framing was wrong about this and carries a correction comment saying so;
   the comment, not the issue body, is the specification.
4. **The evidence is written down.** #92 has the payload, the abort event ids, the five
   call sites and the tests that pin the current behaviour. Read it before re-deriving it.

## Where work happens

`/workspace` is a checkout of this repository at `origin/main` as of launch. Commit and
push per task; `main` in sync with `origin/main` at every task boundary. The engine you are
running was baked at launch: **the fixes you write are not live in your own process** — in
particular, *your* contract violations still abort *your* run, so a task that ends with a
malformed final payload will kill this wave exactly as it killed `deck-phase3g`. Quote your
`task_id`.

## What already exists — do not rebuild it

- **`contract_enforcement.py`** — the retry loop, the two event constants, the
  `extra_validate` hook for semantic (non-schema) checks. Complete. Wire it; do not
  reimplement it, and do not add a second retry loop anywhere.
- **`plan_ingestion.enforce_plan_contract`** (`plan_ingestion.py:480+`) — the one live
  consumer of this shape today, for the file-borne plan proposal. It is the working
  precedent for "re-prompt a hat with its own validation errors" in production; read how it
  threads `prior_errors` into the next attempt before you build the worker's equivalent.
- **`_ask_router`** (`loop.py:2768`) — the precedent for a model call that is deliberately
  **not** an iteration: no `iterations_used` increment, no `iterations/NNNN/` directory, no
  `meta.json`, usage still accounted under `usage.byPhase["router"]`. Requirement B needs
  exactly this shape.
- **`faults.explain_fault`** and **`state.explain_run_fault`** — the fault derivation and
  the run-level join `ralphctl fault` prints. Requirement H extends *where* the first is
  called; it does not change what either decides.
- **`transitions.TABLE["worker"]`** — already declares `T("worker", "no_verdict_yet")`,
  the self-loop for "this iteration produced no usable verdict". Requirement C should need
  no new edge; see there.
- v0.12's home-isolation work, the ambient-`$HOME` allowlist and the sweep-tier discipline.
  Use the sweep scripts as they are — with the single, bounded exception of requirement M,
  which adds one `setenv` to the autouse fixture and one mode to
  `scripts/host_like_dev_layout.sh`. Nothing else in that area is in scope.

# The requirements

## Half 1 — #92: a contract violation is re-prompted, not fatal

### A — the five sites, named

`loop.py` refuses a bad payload in five places, each the same three lines (log, set
`_abort_reason`, `return ("tail",)`):

| line | site | what it validates |
|---|---|---|
| `2516` | `_step_generic_hat` | the hat's schema (`contracts.validate_payload`) |
| `2531` | `_step_generic_hat` | a reported `task_status` move (`_apply_reported_task_status`) |
| `3163` | worker | `verdict: "unsatisfiable"` — schema, then `_apply_unsatisfiable_report` |
| `3187` | worker | `verdict: "complete"` — schema, then `worker_completion_report_errors`, then `_apply_worker_completion_report` |
| `3198` | worker | schema errors on any other verdict |

All five must go through `enforce_contract`. The semantic checks (rows 2, 3, 4) are
supplied as `extra_validate`, **not** as a second validator: `contracts.validate_payload`
stays the only reader of `HAT_SCHEMAS` (fact 16/#65 does not get weakened by this wave), and
`parse_response` stays the only place a raw payload becomes `(payload, errors)`.

Start by writing, in the notes, which of the five you are cutting over in which task and
what each one's `extra_validate` closure is. A single task that does all five at once is
too big and will be rejected.

### B — the re-ask is a cheap re-ask, never a repeated work iteration

This is the wave's one real design decision, and getting it wrong is worse than not doing
the wave.

Iteration 137 of `deck-phase3g` was **11 minutes** of real work that *succeeded* — it
converged call sites, committed evidence, and ran a targeted validation. Re-running it to
fix a quoting slip would burn the time again and might redo committed work. So the retry
must be a *constrained follow-up about the payload only*, in the manner of `_ask_router`:

- it states the specific validation errors verbatim (`$.task_id: expected string, got int`),
  and asks for the corrected final payload — nothing else;
- it must **not** re-issue the hat's task prompt, must not invite further work on the
  workspace, and must not be reachable by a hat as a way to get a second work turn;
- it is **not charged as an iteration**: no `iterations_used` increment, no
  `iterations/NNNN/` directory, no `meta.json`. Its usage IS accounted, under its own
  phase bucket, exactly as the router's is — visible, not hidden;
- every attempt leaves a transcript on disk, in the shape `artifacts/router/NNNN.jsonl`
  already establishes for uncharged calls.

**Acceptance:** a test that drives a worker whose first payload is malformed and whose
re-ask answer is well-formed, and asserts (a) the task moved as the corrected payload
said, (b) `iterations_used` advanced by exactly one, (c) the re-ask prompt contains the
validation error string and does **not** contain the worker task prompt, (d) a transcript
for the re-ask exists.

### C — an exhausted ladder is an agent fault, and the run continues per the table

When `enforce_contract` returns `agent_fault=True`, the harness scores one agent-fault
iteration against the budget and continues per `transitions.py`. It does **not** set
`_abort_reason`.

For the worker, the existing declared edge `T("worker", "no_verdict_yet")`
(`transitions.py:111`) already means precisely "no usable verdict this iteration" — a hat
that never produced a valid payload produced no verdict. Prove that reading is right and use
it; if you conclude a new edge is genuinely needed, say why in the commit message and add it
to the table declaratively, never as a special case in the executor.

For `_step_generic_hat`, decide and record what an exhausted ladder does for a hat with one
declared edge versus several, and why.

**The invariant this requirement exists to establish, and which a test must pin
directly:** *a contract violation may never be the sole reason a run ends while an approach
and iteration budget remain.* Write that test against the concrete `deck-phase3g` shape —
approach 2 of 12, 765 iterations left — and let it name the run.

### D — an engine-side cutoff is still not a contract violation

`_iteration_cut_short_by_engine` (SIGINT, the iteration timeout, the startup watchdog, an
abnormal exit) must be checked **before** the contract pass, and must not consume a retry
or trigger a re-ask: there is no hat to ask, and an absent payload from a killed process is
not a broken contract. This is v0.11's requirement A / #72, and
`tests/test_interrupt_not_substantive_outcome_task004.py:191,208,214` pins it — those
assertions must still pass, unmodified, after this wave. If the new ladder makes them fail,
the ladder is wrong, not the test.

### E — the tests that pin the abort are strengthened, never deleted

Five assertions currently pin the run-ending behaviour:

- `tests/test_worker_harness_owned_status.py:164`
- `tests/test_unsatisfiable_criteria.py:331`
- `tests/test_hat_extensibility.py:214`
- `tests/test_task_status_lifecycle.py:423`
- `tests/test_tier_escalation.py:225`

Each becomes a stronger claim about the same input: the violation was refused (the move was
*not* silently taken — that half is the real content and must not be lost), the errors were
carried back to the hat, the ladder ran to `contract_retry_max`, and the outcome was an
agent-fault iteration that continued per the table. For each, the commit message states what
the old assertion claimed and why the new one is stronger.

`tests/test_task_status_lifecycle.py:15` currently *describes* the intended behaviour —
"re-prompted, logged, and eventually scored an agent-fault, through the EXACT SAME retry
loop" — while `:423` in the same module asserts the abort that bypasses it. When this wave
lands, that docstring becomes true. Say so where you fix it.

### F1 — the `deck-phase3g` regression test

A named test whose input is the exact payload that killed the run:

```json
{"verdict": "complete", "task_id": 104}
```

It must show the run **surviving**: the violation refused, the error carried back, and (on
a corrected re-ask) task `104` moving as reported. Name `deck-phase3g` in the docstring
with its cost, so the next person to read it knows what it is protecting.

### F2 — do not fix this by coercing the scalar

Every id in `tasks.json` is a string, and `prompts/worker.md:50` already shows
`"<the assigned id>"` quoted, so `task_id` *could* be normalised from a JSON number. You may
do that as belt-and-braces, and if you do, record the decision. But it is explicitly **not**
this wave's fix: it repairs one line, and the next violation will be a different field.

If you add coercion, the ladder must additionally be proven against a violation coercion
cannot repair — a bad `verdict` enum value, say — so that no test in this wave passes for
the coercion's reason rather than the ladder's.

### G — the violation is recorded as an event, from the live path

`deck-phase3g`'s `events.jsonl` contains **no** `contract.violation` event. The 736 events
break down as `task`, `skills.placement.verified`, `iteration.start`/`end`, `signal`, `log`,
`state`, `phase`, `infra_*`, `budget_seeded`, `reflect_done` — and the only trace of the
thing that ended the run is one `{"type": "log", "level": "error"}`. So no surface can count
violations, attribute one to a hat, or show an operator what the payload got wrong.

The live path must emit `contract_enforcement.EVENT_VIOLATION` per failed attempt (hat,
attempt, maxAttempts, errors) and `EVENT_AGENT_FAULT` once on giving up — the same events,
with the same fields, `enforce_contract` already emits when given a sink. Then surface them:
`ralphctl status`' reason line and `ralphctl iteration N` must be able to say a hat broke
its contract and what the error was, for an iteration that recovered as well as one that
did not.

## Half 2 — #89: an iteration can say why it failed

### H — derive the fault cause per iteration, not only for the last one

Today the hub shows a faulted iteration as, literally, `error`. `deck-phase3g`'s
`iterations/0137/meta.json` and `selfdev-v012-green-on-a-real-host`'s `iterations/0002/
meta.json` both carry `"error": "aborted"`, `"faultClass": "infra"` — and nothing about why.

**Read #89's correction comment first.** The cause is not missing from disk:
`faults.explain_fault` is a pure function of fields meta.json already carries (`error`,
`exitCode`, `interrupted`, `timedOut`, `noTrafficTimeout`, traffic inferred from `usage`/
`sawComplete`), and `explain_run_fault` (`state.py:3646-3665`) already calls it that way.
The defect is *where* it is called: only for `_last_fault_iteration(root)`. So iteration
#2's cause becomes unreachable the moment #40 faults, though #2's own meta still holds every
input needed to re-derive it.

- `iteration_detail` (`state.py:1388+`) derives `reason` and `signature` for **its own**
  iteration, through the same `faults.explain_fault` call — one shared derivation, not a
  second one, and not a new persisted field.
- Both go into `ITERATION_DERIVED_KEYS` (`state.py:1142`), so a hand-edited or hostile
  meta.json cannot smuggle a cause in — the discipline that tuple already enforces for every
  other derived display value.
- `faultClass` remains the verdict the engine **recorded and acted on**. A re-derivation that
  disagrees is reported as a disagreement (`FAULT_VERDICT_DIVERGED_NOTICE`), never silently
  preferred — and that check becomes available per iteration rather than only for the last.
- **Out of scope, deliberately:** attributing a historical retry *episode* (attempt,
  backoff, outage budget) to its iteration. Those live in `infra_retry`/`infra_wait` events
  and are episode-scoped; keying them by iteration is a separable, smaller-value follow-on.
  If you want it filed, file it — do not smuggle it in.

**Acceptance:** a run dir fixture with two faulted iterations of different causes, where
each iteration's detail names its own cause and the later fault does not overwrite the
earlier one's.

### I — every iteration surface renders it

`ralphctl iteration N`, the hub's timeline row and the hub's iteration dialog all read the
same `iteration_detail`, so all three gain the cause at once. A faulted row reads like
`infra — provider hung up mid-stream`, not `error`.

No new renderer: `ralphctl fault`'s live view already prints these lines and must keep
printing exactly the same ones. If a wording is shared, it is shared through one function,
per this repo's `iteration_detail`/`run_documents` discipline.

**Acceptance:** a browser-tier assertion that the hub's iteration view shows a cause
sentence for a faulted iteration, plus a CLI assertion for the same fixture — proving the
two agree because they derive from one place, not because two strings were kept in step by
hand.

## Half 3 — #90: the planner prompt carries the practices

### J — the plan-building practices move into the prompt

`src/ralphd/prompts/planning.md` (112 lines) already covers a lot: step 2a spot-checks the
PRD's `file:line` claims against the code, 2b measures the test surface against the
iteration cap, and the Rules section demands atomic tasks, independently-checkable
criteria, work-plus-verification sized to one iteration, and no dependence on this run's
own terminal state.

What is missing is the set each recent PRD has had to spell out by hand. Add each with the
incident that taught it — a rule whose reason is stated is followed; one asserted is
lawyered:

1. **A closure is a task with evidence.** Naming an issue is not closing it. (v0.10's
   review rejection.)
2. **A report- or docs-only task still changes the repository**, so it re-verifies the
   guards at the *true final sha*, with `HEAD` and `origin/main` shown to agree. (v0.11
   shipped a red suite; its own re-verify task passed for a machine-dependent reason.)
3. **No task's criteria may *require* a full-suite run** unless it is a sweep task — as a
   prohibition on wording, not sizing advice. (A v0.11 iteration spent 2h and ~$9.30
   hitting the 120-minute cap for zero tasks.)
4. **One sweep task per tier**, bounded and backgrounded, with **every skip named**.
5. **Criteria may only cite paths the repository contains.** (#86: a report cited a
   generated, untracked directory and the guard passed only on the machine that generated
   it.)
6. **A fixed tail order:** work → closures → record → sweeps → guard re-verification →
   closing report. The closing report is never written against an unfinished wave.
7. **Closure tasks `dependsOn` the work they attest to** — list order alone is fragile,
   because a validation-failed task can be reordered.
8. **A sweep task's criteria state its execution shape** using the numbers step 2b already
   measured, rather than leaving each worker to rediscover the runtime.

### K — decide what belongs in a lint instead, and be careful

Some of these are checkable at ingestion, where `plan_ingestion.py`'s own-terminal-state
lint already lives — 5 (cited paths) and 7 (`dependsOn` on closures) most obviously. A lint
beats a paragraph: it cannot be skimmed.

But **#76 is the cautionary tale, and it is closed, not theoretical**: that lint matched its
two cue sets anywhere in the same string, so a perfectly satisfiable criterion *about*
terminal-state behaviour was rejected on vocabulary, and the planner passed the gate by
editing words rather than changing what the task did. Any lint added here must be shown to
reject a genuinely bad plan **and** accept a good plan that merely talks about the same
subject, with both as fixtures.

You may implement one lint, or none, and record the reasoning either way. Adding a lexical
lint that fires on subject matter would be worse than shipping nothing here.

### L — prove the prompt change is live and safe

Prompts are hot-swappable per run (`ralphctl prompts`), and this one is the first thing every
future wave reads. Whatever guards `planning.md` today must still hold — including the
docs/flag consistency guards, which cover teaching docs and will see any command or flag you
mention. A prompt that fails its own guards is not shippable.

## Half 4 — the sweep that would otherwise lie (#93)

### M — the `--user` layout is green again, and the tier can see it

This requirement exists because without it, **this wave's own final sweep is a false
green.** Non-negotiable 9 asks for the developer-host layout to be green at the shipped sha.
It will be — and a real developer host will still be red, for a reason that tier is
structurally unable to observe. Shipping that is v0.11's mistake with a new coat of paint.

At launch, on a host with `pip install --user -e .`, the fast tier fails **498 tests**, 343
of them `No module named 'ralphd'`. One variable is the entire difference:
`PYTHONUSERBASE=$HOME/.local` makes a failing test pass. It is a regression — the same host
and layout ran 3929 passed / 5 skipped / 0 failed at `cfe805c`, the last commit before v0.12.

The cause is five lines, `tests/conftest.py:313-317`: v0.12's autouse in-process `HOME`
isolation calls `monkeypatch.setenv("HOME", …)` and nothing else. On a `--user` install the
user site is `$HOME/.local/lib/pythonX.Y/site-packages`, derived from `HOME` at interpreter
start, so every subprocess that fixture's `HOME` reaches — and ~343 tests spawn `RALPHCTL`
or `RALPHD_ENGINE` — cannot import `ralphd`. `with_ralphd_importable()`
(`tests/conftest.py:77`) already solves exactly this for children reached through
`_resolved_home_env`, and its comment already names `PYTHONUSERBASE` as "the load-bearing
half". The autouse fixture overrides `HOME` out of band and skips it. One path is
protected; the other, added later, is not.

- **Fix the asymmetry**: the autouse fixture also pins `PYTHONUSERBASE`, to the user base
  computed from the *real* ambient `HOME` — reusing the value `with_ralphd_importable`
  already computes once at import, never a second derivation.
- **Give `scripts/host_like_dev_layout.sh` a mode with `PYTHONUSERBASE` unset**, so `HOME`
  alone decides the import path, which is the literal shape of a real `--user` host. That
  script currently computes the user base from its synthetic `$HOME` and **exports** it
  (`:124-155`) — deliberately, per its own header, to make the claim portable — and that
  export is what blinds it, because a real host has the variable unset. Per v0.12's own rule
  for this script, the new mode must be shown to **fail** against a documented one-line
  mutation (reverting the fix above) and pass with it. A mode that passes both ways is
  worthless as evidence.
- **The two halves are mutually exclusive on this layout, and that constrains the fix.**
  With `PYTHONUSERBASE` exported the same tier gives `1 failed, 4077 passed, 5 skipped` —
  and the one failure is caused by the export:
  `test_engine_child_import_path.py::test_the_engine_script_itself_runs_under_an_overridden_home`
  is #67's own reproducer, and its mutation pair (`:284-290`) builds the hostile child env as
  `{**os.environ, "HOME": "/nonexistent-home-for-67"}`, which carries `PYTHONUSERBASE`
  through, so the "broken" spawn stops being broken. 343 tests need the user site to survive
  an overridden `HOME`; that one test needs a spawn where it does not. So the fixture fix must
  come with this test's `fresh_home` built from an environment with `PYTHONUSERBASE`
  **removed**, not copied — otherwise the reproducer is silently disarmed rather than
  satisfied. Grep for `{**os.environ` beside a `HOME` override and check each one.
- The 3 `No module named 'uvicorn'` failures in the same run are a separate, smaller thing.
  Confirm what they are; do not conflate them, and do not fix them here unless it is a
  one-line dev-extra correction.

**Acceptance:** the fast tier is green under a `PYTHONUSERBASE`-unset, `--user`-shaped
layout at the shipped sha, and the mutation evidence is recorded in the sweep report.

# Non-negotiables

1. **Every `loop.py` change has a test that fails without it.** This is the supervisor that
   drives every run. No exception, and "the sweep covers it" is not an answer.
2. **Never a full suite inside a task iteration.** Bound and background every sweep
   (`nohup timeout … &`), then poll briefly. `iteration_timeout_s` is a hard kill.
3. **No blocking `sleep`** as a way to wait for anything.
4. **`timeout 120` on a new module's first run**, always.
5. **Stub `sup.runner`; never call `_run_iteration_once`** in a test.
6. **A re-ask never redoes work and never costs an iteration** (B). If you cannot achieve
   both, stop and say so in the notes rather than shipping a retry that re-runs a
   ten-minute work turn.
7. **Never weaken a test to make it pass.** The five assertions in E change; each commit
   says what the old claim was and why the new one is stronger. D's assertions do not
   change at all.
8. **Commit and push per task.** `main` == `origin/main` at every task boundary.
9. **Sweeps sit at the true final sha**, with `git rev-parse HEAD` and `origin/main` shown
   to agree and **every skip named with its reason**. Record the fast, docker and browser
   tiers plus the developer-host layout (`scripts/host_like_dev_layout.sh`).
10. **Cleanup by exact tag and exact container name only.** Never `docker prune`, never a
    label- or wildcard-filtered `docker rm`/`rmi`.
11. **Reports cite tracked paths.** A run-dir path is written absolutely.
12. **Do not record your own unshipped fixes as exercised.** Your engine predates them —
    and note the sharp edge: your own contract violations still abort this run.
13. **Close an issue only from evidence**, and never write a closing keyword next to an
    issue number the commit does not close.

# Definition of done

1. All five `loop.py` sites go through `enforce_contract`, with the semantic checks supplied
   as `extra_validate` and `validate_payload` still the only `HAT_SCHEMAS` reader (A).
2. A contract re-ask states the validation errors, does not carry the hat's task prompt,
   does not increment `iterations_used`, writes no `iterations/NNNN/`, accounts its usage
   under its own phase, and leaves a transcript — each pinned by an assertion (B).
3. An exhausted ladder is an agent-fault iteration that continues per the table; the worker
   path uses a declared edge; `_abort_reason` is not set (C).
4. A test pins directly that **a contract violation is never the sole reason a run ends
   while an approach and budget remain**, written against `deck-phase3g`'s shape (C).
5. `tests/test_interrupt_not_substantive_outcome_task004.py`'s assertions pass unmodified
   (D).
6. The five abort-pinning assertions are strengthened, each with a commit message saying
   what the old claim was; the `test_task_status_lifecycle.py:15` docstring is now true (E).
7. A named regression test replays `{"verdict": "complete", "task_id": 104}` and shows the
   run surviving (F1); if coercion was added, the ladder is separately proven against a
   violation coercion cannot repair (F2).
8. `contract.violation` and `contract.agent_fault` are emitted from the live path with hat,
   attempt, maxAttempts and errors, and are readable through `ralphctl status` /
   `ralphctl iteration` (G).
9. `iteration_detail` derives `reason` and `signature` for its own iteration, both listed in
   `ITERATION_DERIVED_KEYS`, with `faultClass` still the recorded verdict and divergence
   reported; two faulted iterations of different causes each keep their own (H).
10. `ralphctl iteration N`, the hub timeline row and the hub dialog all render the cause from
    that one derivation, proven by a CLI assertion and a browser-tier assertion over the
    same fixture (I).
11. All eight practices are in `planning.md`, each with the incident that taught it, and the
    file's existing guards still pass (J, L).
12. The lint decision is recorded; any lint added rejects a bad plan and accepts a
    good plan that merely discusses the same subject, both as fixtures (K).
13. The autouse in-process HOME fixture pins `PYTHONUSERBASE`, and the dev-layout script has
