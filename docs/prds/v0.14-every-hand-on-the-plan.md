# v0.14 — every hand on the plan is named

## Goal

#60 is closed. The loop's rules are data, task state is harness-owned and unwritable by an
agent, the status lifecycle is a declared mini-FSM, and every hat reports through a schema.
What that work did **not** settle is who may *change* a plan once it exists, and what
happens when nobody can.

Four things established that gap in the last two waves, all of them from the runs' own
records rather than from theory:

- **`deck-phase3g`, approach 3, ~$231 in.** Task 202 exhausted its validation ladder with
  six tasks depending on it — including the `ci/stability.sh 10` gate the previous
  approach's review had named as *the* thing preventing verification. Neither resolution
  `worker.md` sanctions clears dependency doom: one leaves the task `failed`, the other
  relabels it `skipped`, and both are dependency-dead. It took an out-of-band operator
  amendment **plus** a steer authorising a status change the worker's own prompt forbids.
  (#99)
- **`selfdev-v013-a-broken-contract`, steer 003.** An operator steered one small,
  fully-specified change into a running wave. It was marked `consumed` inside approach 2
  with three quarters of it undone, and became tracked work only because an unrelated
  replan happened to be coming. "Consumed" means *"was in the prompt of an iteration that
  finished cleanly"* — nothing more. (#98, #91)
- **The same wave, three approaches, ~$111.57.** Two of the three were rejected for the
  same sentence: the suite was not green at the shipped sha, because the wave's own closing
  commits landed after its own sweeps. That has now cost **the first approach of every wave
  since v0.11** — four consecutive waves. (#103)
- **A worker that discovers its assigned task is really three tasks** writes prose into a
  50-line file it is also told to rewrite, and hopes a later replan reads it. (#102)

So: four different hands reach for the plan — the operator, the harness, the worker, and
(soon) a peer — and exactly one of them, the planner, has a mechanism. This wave gives each
of the others a named, typed, auditable one, and fixes the two accounting defects that make
a long run unrecoverable when they fire.

It also cashes in the claim #60 pillar 4 made and never tested: *a hat is a state, a
schema, a prompt, transitions and a model role, with no loop surgery.* This wave adds
**three** hats. If the third one needs loop surgery, that is a finding about the table, and
it belongs in the closing report — not a thing to push through quietly.

**Nine issues: #103, #99, #98, #101, #102, #100, #95, #96, #88 — and #91, which closes as a
consequence of #98 rather than by its own work.**

## Pushing, and closing issues from inside the run

The `n-orlov` GitHub credentials are mounted, not something to ask for: `--creds` places
`github.env` at `$HOME/.creds/github.env` (`GITHUB_TOKEN`, `GITHUB_USER`, mode 0600) along
with `gitconfig` and a `git-credentials` entry for `https://n-orlov@github.com`
(`engine/creds.py:place_creds`). So `git push` works without further setup, and the GitHub
REST API is reachable for requirement S's closures — v0.13 closed four issues this way.

- **Source the env file; never inline the token.** `set -a; . ~/.creds/github.env; set +a`,
  then `Authorization: Bearer $GITHUB_TOKEN`. The token must never appear in a command you
  echo, a log, a commit message, a report, an issue comment or a Telegram message.
- **`git remote -v` prints the credential-bearing URL.** Do not run it, and redact any
  push/fetch output you quote (`sed -E 's#https://[^@]*@#https://***@#g'`).
- **Verify a closure with a fresh `GET`**, never from the create call's echo — the discipline
  every wave since v0.9 has used.

## Telling the operator what is happening

This job is started with the `telegram-notify` skill placed and `--network host`, so the
operator's notifier at `http://100.71.162.65:8090` is reachable. **Read
`~/.pi/agent/skills/telegram-notify/SKILL.md` before your first send** — it carries the
endpoints, the `plain`-over-`MarkdownV2` rule and the file-upload form.

Previous waves had the skill placed and never used it, because no PRD asked. This one asks.
The operator is not watching the log; a run that goes quiet for six hours is
indistinguishable from a stalled one.

**Send, at minimum:**

1. **Plan accepted** — approach number, task count, and the requirement letters it covers.
2. **Each task validated** — one line: task id, what landed, and the evidence (test node ids
   or the commit). The skill's own example is exactly this granularity.
3. **Each sweep** — the result *and the log as a file*, not 400 pasted lines. If the sweep is
   red, say what failed and whether it is attributed to this wave.
4. **Each issue closed**, with the comment URL.
5. **Every approach rejection and replan** — the findings in one paragraph. This is the
   message the operator most needs and is the one a struggling run is least likely to send.
6. **Every cut**, the moment you decide it: which requirement, why, and where it sits in the
   cut order. A cut discovered by the operator in the closing report is a cut they could not
   have argued with.
7. **Each decision requirement resolved** — F's third-status ruling, L's rejection semantics,
   K's revision bound.
8. **Terminal state**, with the honest one-paragraph summary.

**And the guardrails, which matter as much:**

- **A notification is never load-bearing.** It is send-only: there is no reply channel. Never
  phrase a message as a question you intend to wait on, never poll for an answer, and never
  let a failed POST fail a task, trigger a retry loop or block an iteration. A connection
  error means the network mode is wrong — note it in the notes file and carry on.
- **Never send a secret.** No `github.env` contents, no bearer token, no `/config/creds`
  material, no environment dumps. The same rule the reports live under.
- **Do not narrate every iteration.** The list above is milestones, not a log tail. If you
  find yourself sending three messages about one task, send one.
- **The notification is not the record.** Everything above still goes in `notes.md`, the task
  record and the closing report. A message the operator scrolled past is not evidence.

# The requirements

## Half 1 — the sweep that has cost four approaches (#103)

### A — a sweep record's sha stops being a sentence and becomes a checkable fact

`docs/prds/README.md`'s own index says the first approach of **every wave since v0.11** was
rejected for the suite not being green at the shipped sha — v0.11 (*"a report-only commit
left the suite red"*), v0.12 (*"the new dev-layout tier was not green at the shipped sha"*),
v0.13 approach 1 (*"RED at the shipped sha from two of the wave's own regressions"*) and
v0.13 approach 2 (*"a docs-only commit … making the fast tier RED at the shipped sha"*).

The trap is structural, not careless: a wave cannot finish without commits that change the
repository (the roadmap block, the index row, the closing report), the repository has guards
that read those files, and so the final commits invalidate the sweeps by construction.

Make the discrepancy mechanical:

- every sweep record in `artifacts/reports/` states the sha it ran at in a **machine-readable**
  form (a fenced line, front-matter, whatever — pick one and document it);
- a fast-tier test reads those records and fails when a record claims a sha that is not the
  current `HEAD`, naming the record and both shas;
- the message says what to do about it (re-take, or re-run the subset from B), because the
  reader will be a hat under time pressure.

Its own acceptance is a fixture: a deliberately stale record fails the tier.

**Do not** make this a warning. Four approaches died to a claim nobody checked; the whole
point is that it now fails loudly, in seconds, in the wave's own suite.

### B — the guard subset a docs- or report-only commit can break, discovered rather than listed

A full fast tier is ~14 minutes (4237 tests, 841s at v0.13's final sha), which is why "just
re-run it at the end" keeps being rationalised away — v0.13 approach 2's closing report
argued the gap away in exactly those terms, and was wrong. But the subset that a docs- or
report-only commit can actually break is trivial: `tests/test_docs_consistency.py` plus
`tests/test_docs_prd_index.py` is **10 seconds, 62 tests**.

Ship `scripts/final_sha_guards.sh` (name yours) that runs exactly the modules which read
`docs/`, `artifacts/` or `README` content — **found by discovery, by grepping `tests/`, not
by a hand-maintained list.** A hand list is what v0.13's approach 3 task 012 attempted; it
exhausted its validation ladder and shipped `failed`. Discovery is the requirement, and its
acceptance is a fixture: a new test module that reads `docs/` is picked up with no edit to
any list.

Then use it on yourself: the last commit of this wave is followed by this subset, green,
recorded.

## Half 2 — a doomed plan is not a stagnant one (#99)

### C — `worker.md` stops confidently recommending a no-op

`worker.md`'s `## Completion signal` offers exactly two resolutions for a permanently
`failed` task: carve the residual gap into a new task and let the failed one stand as
history, or relabel it `skipped`. Both are correct for the deadlock that section solves.
**Neither produces `completed` or `validated`**, and
`state.TASK_DEPENDENCY_SATISFIED_STATUSES` is exactly `("completed", "validated")`
(`state.py:2321`). The same section then forbids *"chang[ing] another task's status while
resolving this one"*, which forecloses fixing the dependents too.

So for any validation-exhausted task with dependents, the prompt recommends a move that
cannot work, and says nothing about it.

Fix the prose: state that neither resolution clears dependency doom, and instruct the worker
to **report the doomed set and stop** rather than pick whichever resolution looks tidiest.
Cheap, and it defuses the trap for every run before any of the machinery below exists.

### D — a doomed plan raises a named fault instead of starving quietly

Worse than the report in #99 predicts, and the mechanism is a two-function disagreement:

- `scheduler.select_next_task()` is **graph-aware**: a doomed `pending` task has unsatisfied
  `dependsOn`, is never a candidate, and selection returns `None`.
- `state.task_is_actionable()` is **per-task and dependency-blind** — `status in
  ("pending", "in-progress", "validation-failed")`, nothing more (`state.py:2429-2437`,
  `:2040`).

`_unresolved_failures()` — the #33 escape that routes a stuck plan to review for a verdict —
returns `[]` whenever *any* task is still actionable (`loop.py:4018-4036`). **Doomed tasks
are pending, so they read as actionable, and the hatch stands down.** Selection then finds
nothing, the worker is handed *"No task is currently selectable … report back — do not
invent a task_id"* (`loop.py:2782-2788`), changes no status, and three of those in a row fail
the approach as **stagnation**. The plan did not stagnate; it became unreachable. The
recorded cause is a misattribution.

Doom's only consequence today is labels plus one append to the notes file per newly-doomed
set (`loop.py:3193-3204`).

Give it a real one. When the doomed set covers the entire actionable remainder, the loop
raises a **named fault** — the doomed set, the dead ancestors that caused it, and the fact
that the plan is now unverifiable — rather than producing three silent no-progress iterations
and a stagnation verdict. Whether that routes to review for a verdict (reusing #33's path),
to a dependency-graph replan, or to a terminal degraded state is yours to decide and record;
what is not acceptable is the current silence.

Pin it in both directions: a plan with a doomed *subset* and actionable work left behaves
exactly as today, and a plan whose whole remainder is doomed produces the fault rather than
the stagnation verdict.

### E — `ralphctl amend --status`: the operator's typed, unforgeable status ruling

`amend` today writes a criteria ruling that binds **review** and nothing else:
`amendment_entries` has exactly two readers, `ralphctl amend` and
`_operator_amendment_review_context()`, and nothing in that path touches `tasks.json`. That
is why the `deck-phase3g` operator's amendment did nothing for the scheduler and a
prompt-overriding steer was still needed.

Add a status ruling to the same channel — the read-only `/config/amendments/` mount an
iteration cannot write — applied by the **engine** at load time:

- validated against `TASK_STATUS_TABLE` / `TASK_STATUS_VIGILANT_DELTA`
  (`transitions.py:378`, `:398`), so an illegal transition is refused rather than written;
- **preserving the record**: `validationAttempts`, `tierLadderExhausted` and the criteria
  text are left exactly as they stand. A ruling is not a claim the criteria were met, and
  it must not be able to look like one — v0.13's *"quietly rewrote the bar it just failed"*
  flag must not fire spuriously, and must still fire for a real rewrite;
- audited: an event naming the operator as the source, visible on the surfaces the way
  `budget_changed` is.

**This is the smallest change with the largest effect** and it needs no model in the loop and
no steering at all — land it before the steer hat, not after.

### F — decide whether the vocabulary needs a third term, and record the decision

#99's suggestion 3 is a status that **satisfies dependents while recording the shortfall** —
because `skipped` overstates the loss and `completed` overstates the delivery, and the honest
case ("the substantive work landed, one stated property did not") has no word.

Decide it. Either add the term — and then `TASK_STATUSES`, `TASK_STATUS_TABLE`, the counts
mapping, `TASK_DEPENDENCY_SATISFIED_STATUSES`, every prompt and every hub label move with it,
which is a wave's worth of blast radius on its own — or record, in `SPEC.md` and in the
closing report, that the vocabulary stays as it is and **why**, with E as the sanctioned
resolution. A one-paragraph justification either way is the deliverable. Leaving it implicit
is what #51 was filed for.

The default this wave expects is **defer, with E as the answer**. Widening the status
vocabulary as a side effect of a nine-issue wave is how a vocabulary gets two words for the
same thing.

## Half 3 — the steer hat (#98, and #91 closes with it)

### G — the hat: a state, a schema, a prompt, a model role

A new `steer` hat whose job is to **reshape state, never to do the work**: it may insert,
update and delete tasks and amend the standing rules, so that an operator's message becomes
first-class work the normal lifecycle then does and verifies. It writes no code.

- a state in `TABLE` reached only through declared edges, refusing an undeclared one like
  every other state;
- an entry in `HAT_SCHEMAS` and one in `STATE_HAT`;
- a prompt in `src/ralphd/prompts/`;
- a **real** `MODEL_HATS` entry with a shipped default (see the `UNRECOGNISED_HAT_FALLBACK`
  trap above) and rungs in the hat × tier matrix.

This supersedes #60's *"deterministic verbatim wrapper, no LLM touches operator words"* and
*"everything is a task"*. The counterexample is in #98: a verbatim wrapper applied to steer
003 would have produced one task whose body was ~150 lines spanning four sub-deliverables, an
ordering constraint against another task, an exclusion list and an instruction to abandon
itself if it competed — under the generated criterion *"the steering instruction has been
carried out"*. Nothing can judge or schedule that.

### H — the authority boundary is the tool surface, not the prompt

Decided, 2026-08-28: **tasks and standing rules only. Budgets stay operator-only.** The hat
may not grant itself iterations, approaches or wall clock. A hat that can extend its own
deadline is a different safety category from one that edits a task list.

Enforce that by **what tools exist**, not by what the prompt asks for. No budget tool in the
set, and a test that asserts the set — so a tool added later to the wrong list fails a check
instead of passing by omission, the same shape requirement A of v0.9 used for the control
plane (#62).

The status-changing tool **calls requirement E's applier**. One place decides which
transitions are legal, emits the audit event and preserves `validationAttempts` /
`tierLadderExhausted`; two callers use it. Defining that twice is how the boundary drifts.

### I — priority, `--now`, and what "settled" means

- **Absolute top priority**: when unsettled steering exists the hat runs next, above
  validation-failed retries and above any pending task, **deterministically** — the router is
  not consulted.
- **All pending steers in one iteration**, in arrival order.
- **`--now`** keeps its meaning (interrupt the in-flight iteration); the forced transition is
  now to the `steer` hat rather than to `worker`.
- **`settled` ≠ `done`.** `settled` is a harness-observable fact: the hat processed the
  message and applied its changes. `done` is the ordinary lifecycle's verdict on the tasks it
  created. Today's `consumed` conflates the two and that conflation is the whole defect —
  steer 003 was `consumed` at iteration 87 with three quarters of it undone.
- The exit gate gets **stronger for free**: instead of discarding a `verified` verdict while
  a steering *file* is pending (`loop.py:3959-3975`, `T("worker",
  "steering_pending_at_verified")` at `transitions.py:146`), the run cannot reach terminal
  success while a **steering-origin task** is non-terminal. Same guarantee, expressed against
  task state.
- **Steering-origin tasks are marked** as such in `tasks.json` and on every surface.
  `tasks.json` being planner-proposed is a deliberate property; an injected task must not be
  indistinguishable from one the planner reasoned about.

`steering/.consumed.json` and its crash-safe at-least-once ordering
(`loop.py:1274-1284`) are subsumed by the task lifecycle — but **keep the at-least-once
property**. It is deliberate, documented, and the reason a dying iteration does not silently
eat an operator's instruction.

### J — uncharged, laddered, and pre-plan left exactly alone

- **Uncharged**, like the router and the v0.13 contract re-ask: an operator message must not
  cost the run a work iteration.
- Invalid contract output gets the **existing** ladder, then scores as an agent fault.
- **Pre-plan steering is unchanged**: prompt-injected into planning, because there is no
  state to manipulate before a plan exists. *"Steering overrides the PRD where they
  conflict"* stays, and plan ingestion's lint checks the proposal absorbed it. This is #60's
  decision for that case and it stands.
- Keep the read-only **context echo** of recent operator messages in every hat's prompt (the
  successor of today's *"pending, not for this phase"* notice, `loop.py:504-510`). The echo
  carries no consumption semantics; the task lifecycle is the single source of truth.

**When this lands, #91 closes**: adding scope to a running approach becomes possible, by a
fourth route none of that issue's three options anticipated.

## Half 4 — the table's promise, tested twice more (#101)

### K — the peer plan review gate

After planning, an opt-in peer model either approves the plan or returns objections that
route back into a planning revision.

Bound the loop — a revision count, explicitly, not "until it agrees" — and decide whether a
peer iteration is budget-charged (it does real reasoning, which argues yes) and record which.
The gate is **off by default**, and a run with it off must produce a transition table
identical to today's.

### L — the peer verdict gate, genuinely blind

After review emits `verified`, an opt-in peer model **blind** re-verifies before the run may
exit; rejection folds findings into the next approach.

*Blind* is a requirement with teeth: the peer must not be handed the reviewer's reasoning or
verdict, or it is a second opinion on an argument rather than an independent judgement. Say
in the prompt and pin in a test what it does and does not receive.

Decide and record whether a rejection means a new approach (expensive; discards a passing
review) or a targeted worker fix-up (cheap; but then who re-runs review).

### M — the router's first live edge, and the fail-fast that must not be skipped

`ROUTER_FALLBACK` is `{}` — *"no shipped state is router-ambiguous today (every real hat
still has a hand-written `_step_*`)"* (`transitions.py:318-323`). **The router has never made
a decision in a shipped run.** It has a schema, a model key, retries, a timeout, cost
accounting under its own phase and UI traceability (#80), all proven against a fixture hat.

A peer gate is the first genuinely multi-edge hat, so it is the first thing to declare a real
`ROUTER_FALLBACK` entry and exercise `router.decide()` in production. Do that deliberately:
a declared fallback guard beside the table entry, and a test that drives the live path rather
than the fixture.

Also: v0.11 ships a start-time fail-fast for an unroutable hat model
(`tests/test_hat_model_routes.py::test_unroutable_hat_model_aborts_before_iteration_1`).
An **opt-in** gate whose configured model has no route in the profile must fail the same way
— never silently degrade into "no gate", which would turn an enabled safety check into an
absence nobody notices.

## Half 5 — the worker's own proposal (#102)

### N — a split, proposed through the contract; budgeted, marked, and no escape hatch

Today: *"do only the smallest atomic first piece of it and describe the remainder precisely
in the notes file so a later planning/replan pass can carve it into a new task"*
(`worker.md`, `## Rules`). The remainder therefore lives in a 50-line file the next iteration
is told to rewrite, and becomes work only if a replan happens to read it — so a wave whose
review passes first time loses the discovery at exactly the moment things went well.

Add an optional `proposed_tasks` field to `HAT_SCHEMAS["worker"]`, ingested through
**requirement N's own reuse of** `plan_ingestion`'s existing lint. Scope it:

- **splits only.** A split is bounded — the work was already in the plan. A discovered new
  task is unbounded scope, and that is what the PRD and the peer plan gate exist to
  constrain. If you conclude otherwise, argue it in the report; do not widen it silently.
- a **budget** — per approach, stated. Without one this is a plan-growth loop.
- **marked origin**, like steering-origin tasks in requirement I, and for the same reason.
- **no stagnation escape.** Proposing a task *is* a `tasks.json` change, so it registers as
  progress against the 3-iteration guard. Pin that a worker which only ever proposes tasks
  still fails the approach — the same hazard v0.9 requirement H had to pin for
  `unsatisfiable`, pinned the same way.
- `dependsOn` coherence checked, because #99 is what an incoherent graph costs.

Then delete the prose it replaces. Two mechanisms for one job, one of them advisory, is worse
than either alone.

## Half 6 — the last untyped claim (#100)

### O — the whole-plan completion marker becomes a contract value

Pillar 1 said the sentinels become schema fields, and almost all of that landed: review's
verdict is contract-only (*"this contract payload is the SOLE channel this method reads"*,
`_review_verdict`, `loop.py:3730-3750`), per-task completion moved onto the JSON verdict, and
whole-run completion after a verdict is the harness's own conclusion from state
(`_outstanding_for_completion`, `loop.py:3512-3527`).

What is left is one channel: `<promise>COMPLETE</promise>`, still the only way to say
*"nothing was assigned to me and every task is already terminal"*, because the `worker`
enum is `complete | no_verdict | unsatisfiable` with no plan-complete value.

- add the value (name it so it cannot read as a per-task claim), valid **only** when no task
  was assigned;
- cross-check it against `_outstanding_for_completion()` exactly as `honoured_complete`
  cross-checks the marker today (`loop.py:3575-3576`), so a false claim is refused on the
  same evidence;
- retire the marker from `worker.md` — **including** the *"Naming the signal in prose"*
  paragraph, which exists only because the channel is textual: a schema field cannot be
  triggered by discussing itself;
- keep emitting the `signal: "COMPLETE"` event; the surfaces and `loop.py:3901-3925` read it,
  and it is not the sentinel;
- `saw_complete` is demoted to an operator-facing diagnostic — the same demotion
  `saw_verified` already had.

A malformed attempt at the field must reach the ladder rather than reading as a silent
no-progress iteration. That is the actual bug: today a badly-phrased marker is
indistinguishable from silence, and three silences fail the approach.

## Half 7 — two defects in accounting (#95, #96)

### P — a paused run does not burn its own deadline

`self.deadline` is fixed at construction — `time.monotonic() + cfg.job_timeout_s`
(`loop.py:214`), with the wall-clock twin `_deadline_epoch` at `:227`. The pause gate is a
separate await, `await self._pause.wait()` (`loop.py:1547-1548`), reached from ~10 points in
an iteration, and neither `pause()` nor `resume()` (`loop.py:343-349`) touches either
deadline field. So a paused run burns `job_timeout_s` while doing no work.

Worse than one-for-one: once the deadline is behind the run,
`min(cfg.iteration_timeout_s, max(60, int(deadline - now)))` (`loop.py:1177-1179`) gives
**every** remaining iteration the 60-second floor. Pausing near a deadline does not cost an
hour of work; it can cost the run.

The engine already draws this distinction for the other kind of not-working wait:
`_note_infra_wait` shifts both fields, republishes `deadlineAt` and emits
`deadline_extended`, on the stated principle that `job_timeout_s` means *"time the job was
actually able to work"* (`loop.py:215-227`). An operator pause is time the job was not able
to work.

**Measure at the wait site, not in `pause()`/`resume()`** — a pause requested while an
iteration is still running should credit only the time the loop was actually parked, and
`_gate()` is the single place that knows it. Emit `deadline_extended` with a reason that
distinguishes an operator pause from an infra wait, and consider a paused-time total in
`status.json` beside `infraWaitTotalS`.

Acceptance includes the 60s-floor case directly: an iteration timeout that would have been
the floor without the extension, and is not with it.

### Q — reflect gets the ladder every other hat has

Five of six contract sites got the re-ask ladder in v0.13. `_reflect_verdict`
(`loop.py:2062-2090`) did not: an absent or malformed `reflect` payload produces
*"response: no parseable 'reflect' contract payload"* and a **degraded** outcome with no
second chance. `selfdev-v013-a-broken-contract` hit it on its first episode.

Wire it into `contract_enforcement.enforce_contract` like the others. Two properties to
preserve while you do:

- v0.12 requirement G already stops an unparseable reflect from overwriting the work's
  verdict. Keep that. The ladder makes a malformed reflect *recoverable*; it must not make a
  failed reflect *fatal*.
- reflect runs after the run is terminal-ish, inside the `finishing` unwind, with
  `REFLECT_TAIL_TIMEOUT_S` bounding it. An uncharged re-ask must not extend that tail
  without bound — state the interaction, and bound it.

## Half 8 — the operator's own agent (#88)

### R — the shipped operator skill can be installed

`skills/ralphd/SKILL.md` exists and is checked against the real parser by
`tests/test_docs_consistency.py`, but getting it onto a machine is manual. It is read by a
coding agent, so it has to be *in* that agent's skills directory to do anything.

Decisions this wave takes, so the seven open questions on #88 do not reopen:

- **`ralphctl skills install`**, with no run id — the existing `skills` verb, distinguished
  by taking no run. (`skill install` singular reads as a typo of the existing verb.)
- **Copy, not symlink**, with a version stamp, so a later `install` can tell *unchanged,
  upgrade it* from *the operator edited it*. A symlink cannot work from a wheel and is
  exactly the shape #83 kept wiping.
- **Refuse when the target differs from what was last installed**, `--force` to override.
  Refusing on local modification is the honest default.
- **Target**: auto-detect `~/.claude/skills/` and `~/.pi/agent/skills/` (both agents
  discover "a directory containing `SKILL.md`"), with `--target DIR` to override.
- **Source works from a wheel**: `skills/` gets the same
  `[tool.hatch.build.targets.wheel.force-include]` treatment `container/` has, with a
  `PACKAGED_FILES`-style test pinning the mapping.
- **Verify, do not just log** — #83's lesson exactly: after placing, confirm the target is
  discoverable by the agent's own rule and say so, rather than reporting success because the
  copy call returned.
- **A `ralphctl doctor` line**: `operator skill: installed / missing / stale (built from
  0.x.y)`.

This is first on the cut list. It is the only requirement in this wave that no run's failure
demanded.
