# ralphd v0.8 — a run a human can interrupt, audit and believe

## Goal

v0.7 made the loop survive its own bad iterations and stopped its surfaces
reporting a previous episode's facts as this one's. It shipped, and then the
first thing an operator did — abort it — exposed the next layer: **the moments a
human touches a run are the moments it is least trustworthy.**

Three of this wave's requirements come from that single abort, and one from the
teardown that followed:

1. **Interrupting a run is unsafe at the seam.** The recorded state goes terminal
   before the post-terminal reflect iteration runs, so for ten minutes the run
   read as finished while its container was still working — and the hub's delete
   button was live the whole time, one click away from destroying the reflection
   mid-write (#56).
2. **The evidence a wave produces is not independently checkable.** Every wave
   ends by recording "the fast lane is green at `<sha>`". On a developer host that
   claim yields 29 failures and a collection error, all environmental — the suite
   assumes it is inside the job container (#57, #50). Evidence only reproducible
   in the environment that produced it is not evidence.
3. **The bookkeeping can be wrong without anyone noticing.** #50 was closed by a
   sentence in a commit body about a *future* wave, and stayed closed for 19
   hours while the wave's own records said it was deliberately open (#58).

The rest of the wave is the backlog that v0.7 deliberately did not take: a
budget top-up that a resume silently discards (#51), a hub that flickers between
two renders (#27), an approach history that is on disk and invisible everywhere
(#24), image artifacts the hub tells you to go copy out with a CLI (#54), and the
one structural deadlock we know about — an operator ruling that cannot reach
review (#26).

The organising principle: **every operator action on a run must be safe at the
moment the surface offers it, and every claim a run makes about itself must be
checkable by a human on their own machine.** v0.7's principle was honesty across
time; this wave extends it across the boundary between the run and the person
watching it.

New this wave, and not a requirement but a rule: **you report your own progress
to the operator over Telegram** (see Cross-cutting). They are not watching your
log.

Every requirement below has evidence from a real run, and every mechanism named
was verified against `d0cc34e` while this PRD was written. Where something is a
judgement call rather than an observation, it says so.

   fixes change the image content hash and are picked up by the **next**

# Phase 1 — the operator's hands

## A. A terminal state is not recorded until the unwind is over (#56)

The operator's report, verbatim: *"once job finishes/aborts, it runs reflect, and
during this job already shows as finished and eligible for deletion — with a
still live container! doesn't seem right. I would expect job to stay in running
state until all done."*

Build the state that says so. The recommended shape, and the reasoning is in the
issue: a distinct **non-terminal** state for the unwind (`finishing`, in
`NONTERMINAL_STATES`), written the moment the verdict is known and carrying both
the settled `verdict` and the terminal state it will become, promoted to that
terminal state when the engine exits. That keeps fact 2's crash-durability — the
verdict is on disk before reflect starts — while `state` stops claiming the
episode is over before it is.

If you conclude a different shape is better (a `terminalPending` field beside a
`running` state, say), argue it in your notes against these acceptance criteria
rather than silently substituting it. What is not acceptable is a recorded state
that permits a destructive action while the engine is still working.

Acceptance:

- A run with `reflect: true` reaching any terminal outcome — succeeded, failed,
  aborted — records a non-terminal state for the duration of the reflect
  iteration, with the verdict and pending terminal state already on disk, and
  flips to terminal when the engine exits.
- `deletion_refusal` refuses during that window, with wording that says the run is
  finishing rather than that it is still working the plan, and `deletion_fields`
  reports the button disabled with **the same sentence** — the existing
  discipline that the endpoint and the disabled button never invent separate
  reasons.
- `ralphctl rm` without `--force` refuses in the window; `--force` keeps its
  escape hatch and the docs say what it costs.
- **A finished `on_complete: idle` run is still deletable from the hub with its
  container up.** Fact 3. This is the regression the obvious fix introduces, so it
  gets its own test.
- Killing the engine during the reflect window still leaves the terminal verdict
  readable: a resume or `ralphctl repair` reaches the same outcome. Asserted,
  because it is the property the current write order exists to protect.
- `ralphctl status` never prints an `ended:` line beside a live in-progress
  iteration. The hub's run detail likewise never shows a terminal pill above a
  running iteration.
- A run with `reflect: false` is unaffected: no `finishing` state, no extra
  transition, no new event.

`resume` discards a live `budget +N` top-up, and `--iterations +N` adds to
`job.yaml`'s value rather than the one every surface displays. Measured twice in

Fact 9 has the mechanism and the precedent. Take direction 1 from the issue —

Acceptance:

## G. Image artifacts preview in the hub (#54)

The hub lists a PNG a job produced deliberately, makes it clickable, and then
tells you to go copy it out with a CLI. Fact 12 has the plumbing; the issue has
the shape.

The security decisions are the requirement, not a footnote — this serves
agent-authored bytes from an origin that also exposes `DELETE /api/runs/<id>` and
is routinely bound to a tailnet address:

Acceptance:

- A server-decided kind — text / previewable image / opaque binary — living next
  to the existing sniff in `engine/state.py`, so `ralphctl artifacts ls` and the
  hub cannot disagree. A `.tar.gz` keeps today's exact `ARTIFACT_BINARY` wording.
- The kind is decided from **sniffed magic bytes, not the extension**: a file
  named `.png` holding a ZIP is not previewable, one named `.bin` holding a PNG
  is.
- A raw byte route resolving the name through `state.artifact_relpath` and
  nothing else — that function is the one traversal guard and its docstring says
  why. A test that would fail if a second resolver were introduced.
- Allow-list `image/png`, `image/jpeg`, `image/gif`, `image/webp`, with
  `X-Content-Type-Options: nosniff` and a `Content-Type` from the allow-list —
  never `mimetypes.guess_type` on an agent-chosen filename.
- **SVG is not previewable, with a test asserting it specifically** and a comment
  saying why, so a later well-meaning "add svg" fails CI instead of shipping
  stored XSS.
- A `Content-Security-Policy` on the hub — it has none today — tight enough that
  the allow-list is not the only thing standing between an agent-authored file and
  the hub's origin.
- An inline size cap, with today's `pull` wording as the fallback above it.
- `app.js` branches on the server's kind, never on a client-side extension list.
- Browser-tier coverage: an image artifact's dialog contains an `<img>` whose
  `src` is the raw route; a tarball's contains the `pull` text.

# Phase 3 — the deadlock we know about

## H. An operator ruling can reach review (#26)

Steering can change what a job **does** and never what review **accepts**. If a
PRD acceptance criterion becomes impossible, there is no channel to relieve it:
review re-derives its criteria from the unchanged PRD every pass, steering is
structurally unreachable from the review phase (`STEERING_ACTIONABLE_PHASES = {"planning",
"worker"}`), and the run burns every remaining approach failing the same finding
with the substantive work complete and independently verified.

Review is **right** to distrust a claim relayed by the thing it is reviewing —
that is the property to preserve. The gap is that the operator has no
authoritative channel of their own.

This is the one requirement in the wave whose shape is genuinely open. Design it
before you build it, in a task of its own whose deliverable is a written
proposal in `artifacts/reports/`, and state in it what distinguishes an operator
ruling from an agent's assertion at the point review reads it — a file only the
host CLI can write, a marker in the run dir the agent's prompts forbid touching,
a signed amendment appended to the PRD the review reads, or something better.
Then build the one you argued for.

Acceptance:

- A written design in `artifacts/reports/` naming at least two candidate
  mechanisms, the trust property each preserves or breaks, and why you chose one.
- An operator can amend or waive a specific PRD criterion, and review sees the
  amendment as **operator-authored** rather than as a claim from the run.
- The agent cannot forge it. A test asserts that whatever the worker can write
  into the run dir does not satisfy review's test for an operator amendment.
- An amended criterion changes the review verdict on a run that was otherwise
  deadlocked; an unamended one still fails. Both directions.
- `ralphctl` grows whatever verb this needs, with `docs/cli.md` and SPEC updated,
  and the review prompt states how it must treat an amendment.
- If the design work concludes this is not buildable safely in this wave, say so
  in the report with the reasoning, mark the task `skipped`, and leave #26 open
  with a comment pointing at the report. That is an acceptable outcome; quietly
  half-building it is not.
