## Goal

v0.14.1 delivered all six of its requirements and was still rejected — on exactly one finding.
The fast tier cannot be green inside a job container, because one test asserts docker-socket
behaviour unconditionally in an environment that has no socket. A wave's verdict must be
achievable in the environment that renders it; right now it is not, for any selfdev wave, ever.

This wave makes the suite green where it actually runs. Three fixes, all small, all in tests
or one shell script — plus the version, the rows, and the record:

- **A (#109)** — the fast tier's one impossible node becomes precondition-aware, and both
  socket directions get pinned hermetically. After A, a job container can produce a green
  fast tier for the first time.

  It is deterministically red on the operator's host today, at this PRD's own sha.

  its own template sentence.
- **D** — version 0.14.2, v0.14.1's index row settled, the roadmap blocks accurate.
- **E** — the closures with evidence, the sweeps, the self-discharging final record, the
  closing report, the terminal summary.

No new subsystems. Expected change set: `scripts/host_like_pytest.sh` (possibly),
`tests/test_host_like_pytest_script.py`, `tests/test_browser_hub.py`,

## What counts as done here

The operator's disposition for this wave, and review should apply it:

- A **documentation gap, a stale sentence, an imprecise phrase in an earlier record, a missing
  cross-reference or a cosmetic defect** is **disclosed, not repaired**. One line in the
  closing report's residual list — what it is, where it lives, that it was accepted — and that
  is the requirement met. Do not open a task for it, do not file an issue for it, do not go

- What is **not** covered by that: the five requirements below, a red test this wave was asked

  notification never sent. Those are the work.
- **One honest attempt per task.** If a task's criteria cannot be met to the letter, satisfy
  the substance, state the deviation in the record and in the notes, and move on.

## Sequencing rule — the trap that took out v0.14.1's task 002

v0.14.1's task 002 was required to widen a matcher AND leave the suite green — but the widening
is exactly what exposed 20 undeclared records that only the NEXT task's backfill could clear.
The criterion was unsatisfiable at its own position in the plan. Do not repeat this shape:

- **No task's success criteria may require a state that a later task creates.** In this wave
  concretely: requirement A must land, validated, BEFORE any sweep that is required to be
  green runs — because until A lands, a green fast tier is impossible in your container.
- If you find such a dependency mid-wave, split the criterion honestly (the enabling half
  first) rather than deviating silently or blocking.

## Planning rules — flat, like the plan that worked

v0.14 approach 1 built a twelve-deep dependency chain and lost every closing task to one
failure. v0.14.1's fully flat 20-task plan survived four validation-exhausted tasks with
nothing blocked. Copy the flat plan.

- **No task may name a task in `dependsOn` unless it genuinely cannot start without that
  task's output.** For a wave this size the answer is almost always "it can". Sequencing
  (A before the required-green sweeps) is the scheduler's ordering concern, not `dependsOn`.
- Never let a docs, report, closure or notification task depend on a code task.
- The closing report depends on nothing; it states what it observes.

## Pushing, and closing issues from inside the run

The `n-orlov` credentials are mounted, not something to ask for: `--creds` places `github.env`
at `$HOME/.creds/github.env` (`GITHUB_TOKEN`, `GITHUB_USER`, mode 0600) with `gitconfig` and a
`git-credentials` entry, so `git push` and the REST API work with no setup.

- **Source the env file; never inline the token.** `set -a; . ~/.creds/github.env; set +a`.
  The token must never appear in a command you echo, a log, a commit message, a report, an
  issue comment or a Telegram message.
- **`git remote -v` prints the credential-bearing URL.** Do not run it; redact any push output
  you quote (`sed -E 's#https://[^@]*@#https://***@#g'`).
- **Verify every closure with a fresh `GET`**, never the create call's echo.
- **Never write a GitHub closing keyword followed by an issue number** in a commit message
  unless that very commit closes that issue.

# The requirements

## A — the fast tier learns where it is (#109)

The probe in `scripts/host_like_pytest.sh` (~line 127) is already correct — `docker` on PATH,
`-S "${DOCKER_SOCK_PATH:-/var/run/docker.sock}"`, and a working `docker version` round-trip —
and it must NOT be weakened. The defects are around it:

1. `tests/test_host_like_pytest_script.py::test_script_filters_the_docker_tier_out_when_a_usable_socket_is_present`
   (~line 200) asserts the filter **unconditionally**, despite its own name. Where no usable
   socket exists — every v0.14.1 job container — the script correctly injects nothing, the
   docker-marked module collects its 4 tests, and the `returncode == 5` assertion sees `0`.
   This single node cost v0.14.1 tasks 017, 018 and 020 their green and the wave its verdict.
2. The script's header comment asserts a job container "always has a real, working docker
   socket". False since v0.14.1. `test_header_makes_no_self_skip_claim_about_the_docker_or_browser_tiers`
   (~line 181) pins parts of that header — keep header, test and behaviour consistent with
   each other after the fix.

**Fix shape — both directions, hermetic, pinned:**

- **Socket present:** a fake `docker` executable on `PATH` (exits 0 for `docker version`) plus
  a real bound unix socket created by the test at a path passed via `DOCKER_SOCK_PATH` (the
  script already honours it) → assert `-m "not docker"` is injected (nothing collected,
  returncode 5). This direction must no longer depend on the environment's real socket.
- **Socket absent:** `DOCKER_SOCK_PATH` pointed at a path that does not exist → assert the
  script's chosen no-socket behaviour. Two acceptable policies; pick one and pin it:
  (i) inject nothing and let the docker-marked tests' own `_docker_available()` self-skip at
  runtime (today's behaviour, minus the broken assertion), or (ii) also inject
  `-m "not docker"` — a deselect is faster and quieter than a skip, and the tier cannot run
  there either way. Whichever you choose, the header text and the header test must agree.
- Do **not** delete the socket-present filter assertion or the probe's `docker version`
  round-trip. The present-direction behaviour is real and stays pinned.

**Proof of done:** beyond the module's own tests passing — **this wave's own fast-tier sweep,
run inside this job container, exits 0** (requirement E records it). That is the first
in-container green fast tier, and it is the point of the wave.

## B — the hub test stops racing the run it watches (#97)

`tests/test_browser_hub.py::test_run_detail_log_tail_collapses_many_delta_thinking_block` is
**deterministically red on the operator's host at `8adf2bc`**: 4 of 4 isolated runs failed,
~4.3s each — well under the test's 30s deadline, so its wait loop is exiting on some satisfied
condition and then failing the exact-count assert. Each failure reads
`expected exactly one collapsed '[thinking…]' line per rich iteration (2: worker + review),
got 1`, and the captured page body shows the run still at `phase: worker`,
`iterations: 2/12`, iteration 2 "running…" — **the review iteration had not produced its
thinking when the assertion fired**. Full history and the fresh evidence are on the issue
(operator comment of 2026-08-30): red 3/3 at `8ad87d8` (v0.13's reviewer, mid-sweep); green
8/8 at `0a1ba72` inside a job container; red 4/4 at `8adf2bc` on an idle host. The filing's
"correlate with concurrent load" theory is falsified — it fails isolated on an idle host.

**The consistent thread is a race:** the test asserts an exact count of 2 while the second
rich iteration can still be in flight. The fix is to make the wait condition await the state
the assertion demands — the *review* iteration's thinking line, or the stub run reaching its
terminal state — before asserting.

**Rules of engagement:**

- The exact-count assertion (`== 2`) is the test's value and **stays**. Fixing this by
  loosening it to `>= 1`, retrying the assert, or try/except is refused in advance.
- `log_render.py`'s `thinking_seen` guard is not the first suspect — it is unchanged across
  both red observations. Only touch renderer code if your diagnosis actually shows a thinking
  line being dropped; that would make this a real hub bug, and it escalates the suite scope
  (see below).
- **Reproduce first, in your own container, and state plainly whether you did.** One prior
  container was green 8/8, so you may not be able to. If you cannot: the race is still real —
  two independent deterministic-red observations exist — so remove it by construction, point
  at the racing code in your record, and state that runtime verification in the red
  environment falls to the operator post-wave.
- Close #97 only if you can name the race and show the fix removes it; run the node 5
  consecutive times and the whole browser module once at the shipped sha, green, in whatever
  environment you have. If diagnosis dead-ends, post an honest findings comment on #97, leave
  it open, and disclose the residual.
