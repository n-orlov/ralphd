# v0.11 — a model per hat, then a model per task

## Goal

Provisioning is the last static thing in the loop. Every hat in a run shares one
`model`/`fast_model` pair chosen by a preset, and every invocation of every hat shares one
global `--thinking` level. A worker fixing a typo and a worker redesigning the privsep
boundary get identical provisioning; so do the verify passes that check them.

This wave closes that in **two halves, in this order**:

1. **A model per hat (#60 pillar 4's model-roles half).** `model_strategy`, the
   strong/fast tier abstraction and `fast_model` are removed outright and replaced by one
   selector per hat with shipped defaults, each carrying its own thinking setting. This is
   the *column*.
2. **A model per task (#68) on top of it.** Three ordinal complexity tiers widen that
   column into a **hat × tier** matrix, resolved at dispatch from task metadata the
   planner already produces and from escalation signals the harness already owns. This is
   the *matrix*.

The order is not a preference. #68 says so itself, in its own header: *"If picked up
before #60, only the planner-annotation half is implementable; the dispatch-time
resolution belongs in the FSM's transition output."* Half 1 is the substrate; half 2 is a
second axis on a table that must exist first. A wave that tried them in one undifferentiated
lump would have no landable midpoint.

**#68 carries an operator-interviewed design with ten recorded decisions and six open
questions.** Every decision is carried forward verbatim into half 2's requirements below,
and every open question is either resolved here with its reasoning or named as an explicit
non-goal. Nothing in #68's design table is renegotiated by this PRD.

## The gateway question is already answered — cross-family is routable today

Half 1's headline capability is a verifier from a different model family than the worker.
That needed a profile that can reach two families at once, and **the operator's
`corp-aigw` profile already does**:

| provider key | `api` | models served (verified against the live gateway) |
|---|---|---|
| `amazon-bedrock` | `bedrock-converse-stream` | `eu.anthropic.claude-opus-5`, `eu.anthropic.claude-sonnet-5` |
| `aigw-openai` | `openai-responses` | `openai.gpt-5.6-sol`, `openai.gpt-5.6-luna`, `openai.gpt-5.6-terra` |

`pi.providers` is a map, model refs are `<provider>/<model>`, and both entries live in one
profile under one bearer token. So a worker on
`amazon-bedrock/eu.anthropic.claude-opus-5` verified by
`aigw-openai/openai.gpt-5.6-sol` is a **configuration**, not a feature — no profile-format
change, no second profile attached to a run, no auth work. #60 pillar 4's "multi-provider
auth stays a one-profile-per-run model" is already satisfied.

Two honest limits on that finding:

- `GET /api/openai/v1/models` returns exactly those three ids, so the profile's model list
  is complete and current, not aspirational.
- **`/api/mantle` is a 404.** AIGW exposes `/api/bedrock` and `/api/openai/v1` only. If
  "mantle" names a *direct* AWS Bedrock route rather than a gateway path, that is the
  already-shipped `examples/llm-profiles/bedrock.yaml` shape (standard AWS credential
  chain) and needs no design change — the per-hat mechanism is provider-count-agnostic, and
  a third ladder entry is one more `pi.providers` key. **Open question for the operator:**
  if mantle is a distinct endpoint you want named in a shipped example, this PRD needs its
  base URL and `api` flavour; without it, the examples use the two providers above.

framework. They exist. This wave adds a resolver beside them and one new field to a
contract that already validates itself.

wave.** Reasons, both worth stating rather than leaving as a silent cut: it is independent
of provisioning and would roughly double the scope; and it is the *first multi-edge hat*,
which means it is also the first thing to exercise `ROUTER_FALLBACK`'s live path — a risk
that deserves its own wave rather than riding along behind a config migration. It goes to
v0.12, and requirement N records that split on the issue so #60 does not read as
half-abandoned.

# The requirements

## Half 1 — a model per hat (#60 pillar 4, model-roles half)

### A — one model selector per hat, with shipped defaults

Replace the strong/fast tier abstraction with a per-hat table. Hats today are the five in
`STATE_HAT` (`transitions.py:278`) plus the router: `planning`, `worker`, `verify`,
`review`, `reflect`, `router`.

```yaml
models:
  planner:  <ref>     # today's "strong"
  worker:   <ref>
  verifier: <ref>     # may be a different family entirely
  reviewer: <ref>
  router:   <ref>     # already exists as router_model
  reflect:  <ref>
```

- Every entry is **defaultable**: an absent hat falls back to a single shipped default ref,
  and an absent table entirely reproduces today's behaviour for a run that configures only
  `model`. A one-model operator must not have to write six lines.
- `model_overrides` stops being an escape hatch and **becomes the mechanism** — per #60
  pillar 4's wording. If the implementation keeps the name `model_overrides` for the table,
  say so and make the docs agree; if it introduces `models:`, `model_overrides` must be
  accepted as its alias for at least this release, not silently dropped.
- `model_for` keeps its signature and its **anti-downgrade rule**: an unrecognised hat name
  must resolve to the *most capable* configured entry, never the cheapest. That rule is
  already stated at `config.py:428-431` for strategy names and its reasoning transfers
  intact — a typo must never quietly make a run cheaper and worse.
- **The table must be reachable from `ralphctl start`, and today's is not.** This was
  measured while preparing this wave, and it is the sharpest single argument for the
  requirement: `model_overrides` (`config.py:202`) is consulted *first* by `model_for`
  (`:420-421`), so per-hat models already work — but **nothing on the host can write it**.
  It is absent from `start`'s job.yaml payload (`cli/main.py:1507-1518`), from
  `_TEMPLATE_SCALAR_FIELDS` (`cli/main.py:1309-1326`) and from
  `_REGISTRY_CONFIG_FIELD_KEYS` (`:1348-1354`). The only way an operator can set it is by
  hand-editing a run's `job.yaml` and using `resume` to re-read it. So the mechanism #60
  pillar 4 says should "become THE mechanism" is currently unreachable by any supported
  path. Acceptance for this requirement therefore includes a **CLI surface** (a repeatable
  `--model` -style per-hat flag, a registry key, and a template key), each with the same
  precedence order the existing model knobs already document: explicit flag > template >
  `<registry>/config.yaml` > profile > default.
- **Worked, verified example to make the acceptance concrete.** The operator's stated target
  configuration is an **Opus planner, a Sonnet worker, and a `gpt-5.6-terra` inspector**.
  All three refs are routable on the `corp-aigw` profile today — terra was smoke-tested
  against `POST /api/openai/v1/responses` while writing this PRD and answered `completed`
  with the same bearer token the Bedrock provider uses. The first two are already reachable
  (they are the profile's `model`/`fast_model` under `model_strategy: balanced`); **the
  third is reachable only after this requirement lands.** That configuration is the
  acceptance test:

  ```yaml
  models:
    planner:  amazon-bedrock/eu.anthropic.claude-opus-5
    worker:   amazon-bedrock/eu.anthropic.claude-sonnet-5
    verifier: aigw-openai/openai.gpt-5.6-terra     # cross-family inspector
  ```

### B — `model_strategy`, `fast_model` and `STRATEGY_TIERS` are removed, and the removal is a first-class migration

#60 pillar 4 says these are "removed outright". They are also live operator configuration:
`config.py:174-175` documents `ralphctl config set model_strategy quality-first` as the
supported way to get the old behaviour, and `MODEL_STRATEGIES` (`:446`) feeds
`ralphctl`'s `--model-strategy` choices.

- Deleting `STRATEGY_TIERS` (`config.py:291-301`) without a migration path **breaks every
  existing run config and every operator muscle-memory command**. So: a config carrying
  `model_strategy` or `fast_model` must either translate deterministically into the new
  table, or **fail at start with a message that prints the equivalent `models:` block** —
  operator's choice which, but it must be one of those two and never a silent ignore.
- `DEFAULT_MODEL_STRATEGY` (`config.py:184`) and its comment about keeping "what ships"
  and "what an unrecognised name degrades to" as two separate decisions must be
  *reproduced*, not deleted: the new table needs the same two constants for the same
  reason.
- `ralphctl --model-strategy` and `config set model_strategy` must not remain as no-ops.

### C — thinking is part of the per-hat bundle, not one global level

Today `cfg.thinking` (`config.py:203`) is passed once at `loop.py:1140` into
`runner.py:150,158-159` as a single `--thinking` flag for every invocation of every hat.

- Each hat's entry resolves to a **(model ref, thinking setting) bundle**. #68 requires
  bundles rather than two independent axes, and half 1 must therefore already be
  bundle-shaped or half 2 has to retrofit it.
- The setting is **provider-shaped**. `pi --thinking` levels are one family's vocabulary;
  the three AIGW OpenAI models advertise `reasoning: true` and their effort knob is spelled
  differently. A bundle entry must be able to carry whatever its own provider expects,
  and a bundle must not force an Anthropic thinking level onto an OpenAI ref.
- A run that sets only the old global `thinking` keeps working: it becomes every hat's
  default bundle setting.

### D — a configured hat whose model has no route fails at start, not at dispatch

Per #60 pillar 4: *"Fail fast at start when a configured hat's model has no route in the
profile."*

- Validate every resolved hat ref against the providers the profile actually declares,
  at startup, before iteration 1. A typo in the verifier's ref must not surface three hours
  in, on the first task that reaches `awaiting-validation`.
- The error names the hat, the unroutable ref, and the provider keys that *are* available.
- This check reads the profile's declared providers. Reaching the gateway to enumerate
  models at startup is **not** required (it would make a start depend on network health);
  if the implementation wants it, it is opt-in and non-fatal.

## Half 2 — a model per task (#68), on top of half 1

Half 2 implements #68 as designed. Its decision table is reproduced here as the contract
for this half; a task that contradicts a row is wrong even if its tests pass.

| # | decision (from #68, operator-interviewed 2026-08-24) |
|---|---|
| 1 | Three abstract tiers `trivial \| normal \| hard`; the plan carries the **label only** |
| 2 | Tiers are **ordinal per hat**; host map is hat × tier → (model, thinking) bundle |
| 3 | Cross-family supported by construction — each hat's ladder is independent |
| 4 | **Planner** annotates the baseline; **harness** adjusts deterministically; **no dispatch-time LLM judgment** |
| 5 | Missing annotation → default `normal`, ingestion lint **warns, never rejects** |
| 6 | +1 tier per validation-failed retry, cap `hard`; effective tier is harness-owned state |
| 7 | Per-task verify runs at `max(effective − 1, trivial)` on **verify's own** ladder |
| 8 | The run-level final verification **always** runs verify's top tier |
| 9 | Steering-injected tasks start `normal` and escalate normally — no special case |
| 10 | Hats with no task in hand keep their static half-1 role |

### E — the tier vocabulary and the hat × tier matrix

- Exactly three tiers, ordinal, in this order: `trivial < normal < hard`. Three because
  planner judgment between *adjacent* tiers stays reliable at three and stops being
  reliable at five; this is a decision, not a starting point to tune.
- The host map widens half 1's column into **hat × tier → bundle**. A hat's three rungs are
  its own ladder: the verifier's `hard` rung may be a different family from the worker's
  `hard` rung, which is the whole point of decision 3.
- **Plans stay portable.** A task record carries the abstract label. Which model that word
  means is host/gateway configuration the planner never sees, so the same plan runs on the
  homelab gateway and on AIGW with different provisioning and identical semantics.
- Defaultability from requirement A survives the widening: an operator who configures one
  model gets all rungs of all hats collapsed onto it, and tiering becomes a no-op rather
  than an error.

### F — the planner annotates a baseline tier, and its absence is degraded metadata

- The task contract gains an optional `tier`. `_TASK_PASSTHROUGH_FIELDS`
  (`plan_ingestion.py:82-89`) already carries an optional `priority` alongside
  `id`/`title`/`successCriteria`/`dependsOn`, so this follows an existing precedent
  exactly — do not invent a parallel channel.
- The planner is the annotator because it is **the only hat that has read the whole PRD and
  sized the work**, so the annotation costs zero extra LLM calls. Nothing else may annotate.
- Missing or unrecognised → **`normal`, and the plan-ingestion lint warns**. It must not
  reject: escalation corrects under-estimates anyway, and old plans must keep working.
  `validate_proposal_shape` (`plan_ingestion.py:95-122`) is where the shape check lives and
  where the warning belongs — note that it returns *errors*, so a warning channel may need
  adding rather than reusing that list.
- **Degenerate-distribution warning** (#68 open question 5, resolved: include it, cheaply):
  if a plan marks every task `hard`, the lint says so once. Warn only — a genuinely hard
  plan is legitimate, and this is an observation for the operator, not a gate.

### G — escalation is +1 tier per validation-failed retry, and the effective tier is harness state

- Each `validation-failed` re-entry bumps the task's **effective** tier one step, capping at
  `hard`. `TASK_STATUS_TABLE`/`TASK_STATUS_VIGILANT_DELTA` (`transitions.py:378,398`)
  already distinguish a validation-failed re-entry from a first dispatch, so the trigger is
  pure harness logic on state that exists. No new lifecycle edge.
- Baseline and effective tier are **harness-owned task state** (pillar 1): persisted with
  the task record, never writable by an iteration, and **visible in the hub**. The hub's
  task row fields are built at `state.py:1529+`; the effective tier belongs there as a raw
  field, not only inside rendered text.
- **De-escalation does not exist.** #68 omits it deliberately and this wave keeps it
  omitted. A task that got hard once does not get cheap again.
- A task that fails validation *at* `hard` has exhausted the ladder. Record that
  exhaustion as a distinct, queryable fact — it is #61's stagnation input, and the two
  guards should share the "this task is a wall" evidence rather than each deriving it.

### H — verify provisioning: one step down, never a bottom-rung rubber stamp

- Per-task verify runs at **`max(effective tier − 1, trivial)`** on the *verify hat's own*
  ladder, computed from the tier the work **actually ran at** (post-escalation), not as
  planned. Checking is cheaper than doing; a thrice-escalated task still gets a serious
  check.
- The **run-level final verification — the pass whose VERIFIED verdict ends the run —
  always runs verify's top tier.** Economise per task, never on the exit gate. This is
  decision 8 and it is not subject to a cost argument.

### I — scope of application, stated so the boundary is testable

- Applies to **task-scoped dispatches only**: worker, and the per-task verify/review that
  services pillar 3's `awaiting-validation` checks.
- Hats with **no task in hand** — planning, reflect, run-level review — keep their static
  half-1 role. Equivalently: they always run their ladder's designated tier. This must be
  asserted, not assumed, because it is the difference between a resolver and a global.
- **Steering-injected tasks start at `normal`** and escalate like any other task. A
  deterministic wrapper cannot assess an operator's prose, and `normal` + auto-escalation is
  the same rule an unannotated task already gets. No special case, no new tier.

### J — resolution lives in a pure resolver, not in the transition table's output

#68's open question 4 asked whether resolution belongs in the table's output or in a
resolver applied to the router's `(hat, task)` result, and leaned resolver. **Resolved:
resolver.**

- The transition table stays about *what happens next*; provisioning is *how*. Mixing them
  would make `TABLE` carry cost policy, and `transitions.py` is the one module whose
  readability the last two waves were spent buying.
- The resolver is a **pure function** of `(hat, effective tier, host map)` → bundle, with no
  I/O and no clock, so it is exhaustively testable as a table: every hat × every tier ×
  the defaulted and fully-specified map.
- It is applied at the existing dispatch point, `loop.py:1081`
  (`model = self.cfg.model_for(phase)`) — the single place a phase's model is chosen today.
  One call site, not a new pathway.

### K — per-tier spend is visible, or the feature cannot be judged

#68 open question 6, resolved: in scope, minimally.

- `ralphctl status --json` and the hub expose **spend and iteration counts broken down by
  tier**, so "what did tiering actually save" is answerable from the run record without
  re-deriving it from `events.jsonl`.
- The existing derived-cost machinery already attributes spend per phase; this is that
  attribution gaining a second key, not a new pricing path.

### Explicit non-goals for half 2

- **Adjustment signals beyond retry count** (#68 open question 1). Task age, blocker
  discovery and diff size each need a deterministic definition and none has one yet. Retry
  count only. Record the others as still-open on the issue.
- **Any dispatch-time LLM judgment of complexity.** Decision 4, non-negotiable: the router
  stays deterministic-first per pillar 2.
- **De-escalation.** See requirement G.
- **Tuning the tier count.** Three is decided.

## Half 3 — the cheap closures, and the record

These are already root-caused to exact lines, touch no dispatch code, and cannot collide
with halves 1 and 2. They are here because they are nearly free, not because they are
related.

### L — one spelling of "done" (#77 and #78 are one bug)

v0.9 split the terminal success status by mode (`loop.py:2484`:
`target = "awaiting-validation" if self.cfg.vigilant else "completed"`) and left two
readers spelling done as the literal `completed`:

- **#78, the real defect:** `_all_tasks_completed` (`loop.py:3319-3325`) returns
  `all(t.get("status") == "completed" …)`, so for a vigilant run — whose tasks terminate at
  `validated` — it can **never** be true. The grace-review gate behind it is silently dead
  code for every vigilant run ever executed.
- **#77, the visible one:** `format_task_fraction` (`state.py:2063`) takes its numerator
  from `counts.get("completed")` alone, so a fully-validated vigilant run reports `0/17`
  across four surfaces. `TASK_COMPLETION_STATUSES` (`state.py:1693`) already names the
  right set — `("completed", "validated", "skipped")` — and is simply not used here.
- `format_task_counts` (`state.py:2045-2049`) skips `("total", "completed")` when listing
  the remainder; whatever the fix does, it must also skip `validated` or the sentence
  double-counts.
- `_TASK_COUNT_KEYS` (`state.py:686-687`) maps only three statuses, so `validated` passes
  through as its own key — that is why the hub can count it but not render it.
- Finish the operator-facing half: publish **`tasksValidated`** and
  **`tasksAwaitingValidation`** from `TaskRead.row_fields` (`state.py:1529+`). The hub
  cannot render a task lifecycle it is never sent, and that — not the fraction — is what
  makes the list view legible during a vigilant run.

### M — the plan-time terminal-state lint is scoped to a clause (#76)

`lint_own_terminal_state` (`plan_ingestion.py:287-304`) flags a task when any of 7 cue
phrases (`:246-254`, including the bare `"terminal state"`) and any of 12 precondition
words (`:266-269`) appear **anywhere in the same string**, with no clause scoping and no
proximity requirement. So it fires on subject matter rather than structure, contradicting
its own docstring's promise.

- Evidence it is a false positive and not a catch: it rejected v0.10's plan twice
  (`selfdev-v010-not-a-verdict`, `contract.violation` at 07:48:36Z and 07:49:33Z, ~7 minutes
  and 2 iterations), and the accepted third attempt differed **only lexically** — "a
  distinct terminal state" → "a distinct run-state value", "before review returned a
  verdict" → "while review was still unjudged". Same requirements, same tests, same
  artifacts.
- Fix shape: require both cues **in the same clause** (split on sentence/clause boundaries,
  or a bounded window), not anywhere in the string.
- Fixtures, both directions, in `tests/test_plan_ingestion.py` which already tests both:
  v0.10's attempt-2 criteria **must pass**; `TASK_042_SUCCESS_CRITERIA`
  (`plan_ingestion.py:234-239`) **must still fail**.
- **Do not widen the escape hatch by deleting cues.** Task 042's incident was real and this
  guard has to keep catching it.

# Non-negotiables

1. **Every new test module's first run is under a hard wall-clock cap:**
   `timeout 120 .venv/bin/python -m pytest -q <module>`. Exit `124` means a harness bug, not
   a slow test. v0.10 lost **2h23m of an 8-hour wave** to two hangs that this rule would
   have caught in four minutes.
2. **Stub `sup.runner`, never `_run_iteration_once`.** `_run_iteration_once`
   (`loop.py:1053`) is the only place `iterations_used` moves, so a stub replacing it makes
   `budget_left()` true forever and any `while not budget_left()` loop spins at 100% CPU.
   That is precisely how v0.10 lost 95 of those minutes. Any test whose assertion mentions
   the budget uses the `sup.runner` seam.
3. **Bound and background every sweep**: `nohup timeout 2400 … > file 2>&1 &`, then poll.
   Never block an iteration on a foreground suite run.
4. **The docker tier cleans up by exact tag and exact container name, never by label or
   wildcard.** No `docker prune`, no label-filtered `rm`. v0.10 proved this works and left
   zero strays; do not regress it.
5. **A sweep is recorded at the final code sha**, with `git rev-parse HEAD` and
   `origin/main` shown to agree, and every skip **named with its reason**. A green with an
   unexplained skip is not a green.
6. **No silent scope cuts.** If a requirement is dropped for time, say so in the record with
   the reason, and comment on its issue. A deferral stated honestly is a good outcome; a
   deferral discovered by the operator later is not.
7. **Do not touch `~/Projects/agent-sessions-tui`** or any other live run's workspace.
8. **Never write a GitHub closing keyword followed by an issue number unless that commit
   closes that issue.**
9. **Half 1 lands before half 2 begins.** Not an ordering preference — half 2's matrix is a
   widening of half 1's column, and there is no partial-credit state in between worth
   having.
