## Materiality rubric

Review computes its verdict from **blocking** findings only; **residual** findings are recorded
in the engine's run record and never reject. This section restates `docs/review-economics.md`'s
rubric for this contract and narrows nothing.

**Blocking** — any of:

- a red test at the **final code sha** (the last commit that touches anything outside
  `artifacts/reports/`, `docs/roadmap.md`, `docs/prds/README.md`), on a fresh clone of `main`;
- a requirement of this contract (A–K) not met, or a Definition-of-done predicate false;
- a false claim in a tracked artifact that changes what a reader believes **landed or its
  result**: a commit attributed for a change that shipped differently, a test result misstated,
  an issue state misreported, an invented send;
- an issue closed without evidence; a secret exposed; a weakened test or guard; a test deleted
  without the behaviour it pinned being covered by a named surviving test in
  `docs/test-suite-audit.md` § "Subsumed".

**Residual** — everything else, explicitly including: a report, roadmap block or index row that
is stale relative to commits made after it; a missing or imprecise count, sha or
cross-reference; a notification that was not sent, sent late, or not logged; a sweep or guard
record whose declared sha has a report-only gap to `HEAD`; a closing report that does not
mention a petition, adjudication, steer or ruling; formatting; prose infelicity; an inaccuracy
in a record *about another record*; the exact text of a command a task ran, its polling
cadence, a liveness check, or the shell it wrapped a launch in, when the deliverable the
command was for is present and its result verifiable; a numeric target missed **and disclosed
with its measured number** where this contract says disclosure is the fallback; a lane that
went red on a node this contract's own K.3 protocol re-ran green at the same code sha, with
every attempt on the record. A residual finding may be listed, never used to reject, and never
turned into a task by the reviewer.

**Curable findings are specifications.** A blocking finding marked `curable: true` states the
observable that must hold once cured — which file, status, node or number, measured how, at
which sha — and names the recorded evidence the cure will invalidate. A finding that only
describes the defect is a malformed finding (E.2 makes the engine say so).

## Petitions and late cure

The petition protocol and late-cure rule of `docs/review-economics.md` apply. Petitions go in
`artifacts/reports/v0.20-petitions.md` (committed ahead of launch); the run never adjudicates
its own petition and never records an adjudication it has not received. A missed duty is cured
late and labelled late; a late cure is a residual, not a finding. Petitions from
`v0.15`–`v0.19.1` files are history: do not act on their remedies or edit their files.

## What this PRD deliberately does not ask

These clauses sank earlier runs and are banned from this contract, from this run's plan, and
from every success criterion the planner writes; plan_review refuses them:

- **No "last commit" rule; no record about its own future; no per-task notification ledger; no
  sha-scoped-count rule; no sweep-sha rule beyond the existing guard; no audit range; no
  "exactly once"; no protected-path clause; no self-referential criterion.**
- **No exact-command-line criterion.** A criterion names the *observable* a command must
  produce — a file, an exit-status file, a tally line, the sha the tree was at, a test node
  passing — never the literal text of the shell line that produced it.
- **No criterion that demands a launch form and a captured result of the same process.**
- **No dependency on a task that can fail for a reason outside its deliverable.** Docs, report,
  record and closure tasks depend only on the code task whose result they describe, never on a
  measurement task.
- **No task whose completion requires another task's future state**, and **no task whose
  criterion is a wall-clock time.**
- **No unenumerated every/each/all quantifier**: name the members, or name the one file or
  command that bounds the set.
- **No criterion that this run's own `status.json`, `events.jsonl` or terminal state must show
  a behaviour this wave builds** — the engine running you predates it.

# The requirements

## A — progress is corroborated, not diffed (#156)

The operator's design decisions on #156 (comment of 2026-09-07) are the specification. Five
stages, five tasks:

1. **The claim.** The worker contract accepts `progress: {"summary": <str>, "evidence":
   [{"kind": "commit"|"file"|"external", "ref": <str>}, ...]}` alongside `no_verdict`.
   `worker.md` documents it; a `progress` block on any other verdict is ignored and logged.
2. **The corroboration.** The engine fingerprints the workspace tree at iteration start and end
   (content hashes over tracked and untracked-but-not-ignored files; git-agnostic, so a
   workspace without `.git` works). `commit`/`file` evidence is corroborated iff the fingerprint
   changed; `external` evidence is honoured at face value **once consecutively** — two
   external-only claims in a row with no tree delta are uncorroborated. Recorded per iteration
   as `progress_claim` with `corroborated: true|false` and the delta size.
3. **The budget.** A corroborated `no_verdict` on task T counts against T's own budget,
   `estimatedIterations + 2` (D supplies the estimate; default 1 when absent), never against
   the approach's stagnation counter. An uncorroborated `no_verdict` keeps today's three-strike
   witness rule. `taskAbsorptionStreak`'s forced verify (v0.19 B.2) is **replaced** by this
   budget: a task under budget with corroborated progress is not forced to verify.
4. **The surface.** `status.json` carries `progressBudget: {taskId, used, budget}` for the
   in-progress task; `ralphctl status`, `ralphctl tasks` and the hub show it; `health` is
   unaffected (progress is not infra).
5. **Pinned** at the in-process tier: corroborated claim does not stagnate; uncorroborated claim
   does; two external-only claims stagnate; budget counts per task and resets on task change;
   the v0.19 #156 approach-1 incident (13 commits over three `no_verdict`s) replayed against a
   stub engine survives.

## B — exhaustion is a split, then a pause, never a replan (#156, #162)

1. **First exhaustion forces a split.** When T's budget is spent, the next worker iteration on T
   is dispatched with the budget-exhausted notice and **must** return `proposed_tasks`; a
   report without one is a contract violation on the ladder. On acceptance the parent becomes
   `superseded` (a new terminal-for-scheduling status: not schedulable, not blocking, its
   `dependsOn` inherited by the children), so the children are picked next.
2. **Splits may depend on the parent's neighbours.** `plan_ingestion.lint_worker_split`
   resolves `dependsOn` against the proposed batch **and** the current `tasks.json` (#162); an
   id in neither is refused with a hint naming both sets.
3. **Second stall pauses.** If a superseded task's children exhaust their budgets too, or the
   approach's witness counter reaches its limit while the branch gained commits during the
   approach, the engine takes the v0.19 B.3 pause (`paused`, `operator_escalation`,
   notification) **on every approach**, not only the last; `resume` re-enters the same
   approach. A repository that gained commits this approach is never replanned for stagnation.
4. `docs/architecture.md`, SPEC.md and the transition table gain `superseded` and the
   every-approach pause edge; the mermaid follows.
5. **Pinned**: forced split on exhaustion; refused split without `proposed_tasks`; `superseded`
   parent not picked, children picked; `dependsOn` on an existing id accepted; the pause on
   approach 1 of 3 with commits present; the unchanged `replan` for a genuinely silent approach.

## C — a `deferred` verdict (#156)

1. The worker contract accepts `{"verdict": "deferred", "until": <ISO-8601>, "reason": <str>}`.
   The task moves behind every runnable task and records `deferredUntil`; the picker offers the
   next independent task; `deferred` never counts as stagnation and never spends the task's
   budget.
2. When nothing is runnable and at least one task is deferred, the engine sleeps until the
   earliest `until`, bounded by `deadlineAt`, recording `deferred_wait` with the bound it used;
   an `until` past `deadlineAt` is refused at the contract with the deadline in the hint.
3. `ralphctl tasks` and the hub show `deferred until <t>`; the worker prompt lists deferred
   tasks with their times.
4. **Pinned**: reorder; picker offers the next task; the sleep bound; refusal past the deadline;
   the v0.19 approach-2 incident (a 06:00Z gate) replayed against a stub engine survives.

## D — the planner sizes tasks (#157)

1. `plan-proposal.json` tasks carry `estimatedIterations` (integer ≥ 1); `plan_ingestion`
   defaults a missing one to 1 and records that it defaulted. `planning.md` documents it.
2. `plan_review` (and the ingestion lint when the peer gate is off) **refuses** a task with
   `estimatedIterations > 3` unless the proposal decomposes it into staged tasks with their
   own measurable criteria — intermediate numeric targets, or named module groups — naming
   the offending task.
3. **A numeric target far from its baseline is a smell.** A criterion of the shape
   `<metric> under <target>` whose plan-quoted baseline is more than 2× the target is refused
   unless the plan names the measurement task that re-measures the baseline at the launch sha
   and stages the descent.
4. The estimate feeds A.3's budget; `ralphctl tasks` shows `est` per task.
5. **Pinned**: default; refusal at 4; acceptance at 3; the 2× rule; the budget derived from the
   estimate.

## E — a cure is not a replan (#167, #171)

1. **A progress-based cure budget.** A second rejection in the same approach takes another
   cure pass iff the new blocking set is not a superset of the previous one (by `clause`), up
   to a ceiling of 3 cure passes per approach; otherwise it falls to `rejected_approach_left`
   as today. `approach.cure_pass` records `blockingBefore`, `blockingAfter`, `passNumber`.
2. **Cure criteria are specifications.** Structured findings gain `cured_when` (required when
   `curable: true`) and optional `invalidates: [<path>, ...]`. `insert_cure_tasks` uses
   `cured_when` as the cure task's `successCriteria` and `clause` + `evidence` as its
   description; a curable blocking finding without `cured_when` is a review contract violation
   on the ladder. `cured_when` passes the bounded-criteria lint like any criterion (#143).
3. **Re-take what a cure invalidates.** For each path in `invalidates`, the engine appends one
   re-take task (`dependsOn` the cure task) whose criterion is that record re-taken at the tree
   the cure leaves; a cure finding against the final-sha sweep re-opens the sweep's launch and
   record tasks in the same `insert_cure_tasks` call, with `dependsOn` chained cure → launch →
   record. The event names every task the pass inserted.
4. **Cure tasks land before the frozen tail.** Cure tasks that touch code are inserted before
   the plan's named last-code-touching task in schedule order; re-take tasks after it.
5. **Pinned**: budget granted on a non-superset second rejection, refused on a superset, ceiling
   3; `cured_when` becomes criteria; missing `cured_when` re-asked; `invalidates` inserts
   dependent re-takes; the v0.19.1 approach-2 incident (one test fix after a recorded sweep)
   replayed against a stub engine ends `verified` in one cure pass.

## F — an approach has a name (#172, #168)

1. Every hat's `## Job context` carries `approach N of M`, `curePasses` for N, and the
   remaining iteration budget, rendered by the engine from `status.json`.
2. `write_amendment` stamps `approach:` in the fixed header; `ralphctl amend` gains
   `--approach N` and prints the target task's current title and status before writing,
   refusing an id absent from the plan without `--force`.
3. `_operator_amendment_review_context` renders as binding only entries whose `approach:`
   matches the current one; earlier approaches' entries render under a labelled *historical
   rulings* heading; an entry naming an id absent from the current plan is not rendered as
   binding and emits `amendment_target_not_in_plan` once per render. An entry with no
   `approach:` key is treated as current iff its id is in the plan (backward compatible).
4. **Pinned**: the Job-context render per hat; approach-1 ruling on `010` not binding in
   approach 2's review context; orphan emits once; no-header compatibility; `amend` echo and
   refusal.
