# ralphd v0.6 — first-release polish: honest cost, honest tasks, a real image lifecycle

## Goal

Close the nine issues filed after the v0.5 wave (#14–#22) and, unlike every
previous wave, **close them on GitHub from inside this run**. ralphd is one wave
away from its first release; what is left is not new capability but the last set
of places where the product lies to its operator or makes them do by hand what
it could do itself:

- cost reads `$0` or `unavailable` on a gateway route whose rates are perfectly
  knowable (#14),
- the task table blinks empty while the agent is writing to it (#15),
- the approach counter has no denominator, so "retry" and "job over" look
  identical (#16),
- steering is write-only: you cannot see what is queued or what landed (#17),
- most of what explains a run is a filesystem path an operator has to go find
  (#18),
- deleting a finished run takes two commands and is impossible from the hub (#19),
- **the job image is never built by anything**, so a run can silently execute a
  ten-day-old engine — which is exactly how #14 came to be reported (#20),
- the run list cannot answer "how far along is this job" without opening every
  run's detail page (#21),
- and the packaging metadata, the version string and two evidence reports say
  things nothing checks (#22).

The organising principle: **every number a surface prints must be either true or
visibly unknown, and every artifact a run produces must be reachable from the
surface that mentions it.** v0.5 established that for cost (`unknown` is not
`$0`); this wave finishes the job for tasks, approaches, steering, faults and
images.

# Phase 1 — stop printing wrong numbers

Requirements A–D. A blocks D; do A first.

## A. A mid-write `tasks.json` must never be served as "no tasks" (#15)

Tasks vanish from the hub table for one poll cycle and come back, and the
`tasks: n/m` counters go briefly wrong, because every reader turns a parse
failure into empty:

- `engine/state.py:427` — `read_tasks()` is `read_json(self.tasks_file, {})`,
  feeding `GET /tasks` (`engine/api.py:137`) and the `tasks` counts in
  `GET /status` via `task_counts` (`engine/state.py:316`).
- `cli/ui_server.py:61` (`_read_json`) and `:345` swallow `JSONDecodeError` and
  return the default.

Harden the **read path** so one fix covers every surface regardless of how the
agent writes the file:

- On `JSONDecodeError`, re-read briefly (bounded, a few tens of ms — the write
  window is milliseconds) before concluding anything.
- If it still will not parse, serve the **last successfully parsed** payload and
  flag it stale. Unknown is not zero; this is #10's cost principle applied to
  tasks.
- Distinguish the three cases that currently collapse into one default:
  **absent** (no plan yet — empty is correct), **unparseable** (serve last-good,
  flag stale), **parsed but empty** (empty is correct).
- Surface the stale flag where an operator can see it, in the style the hub
  already uses for its on-disk-snapshot label. A stale flag that nothing renders
  is not a fix.
- The last-good cache must survive an engine restart the way the rest of run
  state does, and must not become a second source of truth: it is a *fallback
  for a file being rewritten*, never a mirror the engine writes to on the happy
  path.

Not doing the alternatives, both considered: an engine-maintained atomic mirror
adds a second source of truth; telling the agent to write atomically is an
unenforceable instruction to an LLM, and readers would still have to cope.

**Tests.** A reader polling while a truncated/partial `tasks.json` is on disk
never observes an empty task list — assert on all three surfaces
(`GET /tasks`, the `/status` counts, `ralphctl tasks`) and on the hub table.
Assert the three-way absent/unparseable/empty distinction directly. A browser
test that drives an agent-style rewrite and asserts the table does not blink.

## B. Approach `n/m` on every surface (#16)

`max_approaches` defaults to 3 (`engine/config.py:94`); approach 3 of 3 is a
materially different situation from 1 of 3, because a failed review on the last
approach ends the job instead of starting over. Nothing on screen says which.

- Render `n/m` in the hub run list (`cli/web/app.js:119` column, `:316` cell),
  hub run detail (`:427`), `ralphctl status`, and `ralphctl runs`.
- Add `maxApproaches` to `status.json` so no surface has to ask `/config` to
  render its own cell, and so the denominator still exists for a terminal run
  whose container is gone (the on-disk-snapshot path has no `/config` to ask).
  Backfill semantics: a `status.json` written before this change has no such
  field — render `n` bare rather than inventing a denominator.
- A run with no approach yet renders empty, not `/3` with a blank numerator.
- Sorting on the approach column stays numeric on `n` (`app.js:159`).

**Tests.** Hub and both CLI surfaces render `2/3` from on-disk state with no
live container; a pre-v0.6 `status.json` renders without a denominator and
without crashing.

## C. Derived cost from a built-in AWS Bedrock table, and a model id you can see (#14)

AIGW quotes no cost block and its model ids (`aigw-openai/openai.gpt-5.6-sol`)
are local to the gateway, so no upstream table can ever resolve them. The
host-side `pricing:` map (`engine/pricing.py`, inlined by `cli/main.py:718-723`)
already solves this mechanically but requires hand-writing every rate, which is
why it is unset in practice. AIGW bills exactly Bedrock list price for the
corresponding model, so the rates are knowable without operator input.

- Ship a **built-in AWS Bedrock rate table** inside ralphd, plus a bundled alias
  table mapping gateway ids to canonical Bedrock ids (`aigw-openai/* →
  openai/*`, `eu.anthropic.* → anthropic/*`, and the region-prefixed Bedrock
  forms). Reuse `PricingMap`'s existing matching rules (exact, then longest
  prefix, single trailing `*` only; cache rates fall back to the input rate,
  never to zero) rather than writing a second resolver.
- Select it with **`price_strategy`**, set **in the LLM profile** — the profile
  is the thing that knows this route is Bedrock behind a gateway, so the pricing
  knowledge belongs with the route. Override per run with
  `ralphctl start --price-strategy {aws,none}`, persisted into `job.yaml` and
  replayed by `resume` like every other start flag. Deliberately **not** a
  registry-wide `config.yaml` default: it is a property of a route, not of a
  machine.
- Precedence, explicitly: an operator `pricing:` map wins over the built-in
  table; `price_strategy: none` is the default and must leave today's output
  **byte-identical**.
- Cost derived this way stays **derived** — `costDerivedUSD`, `costDerived`, the
  `~… derived` marker in `state.format_cost` (`engine/state.py:166`). A built-in
  table is not a provider quote and `costUSD` must keep meaning "money the
  provider itself quoted".
- Extend `pricing.describe()` (`engine/pricing.py:184`) so `GET /config` names
  *which* table produced a rate: operator map, built-in AWS table, or neither.
- The table needs a documented refresh path (where the numbers came from, how to
  update them, as-of date) and a visible staleness signal, because AWS changes
  prices. A rate table with no as-of date is a future lie.
- **Record the resolved model id in run state.** All three runs inspected have
  `model: None` in `status.json`, so an operator debugging "why is this
  unpriced" cannot see what the engine saw. Record the resolved id and, where it
  differs, the raw gateway id.

**Tests.** A stubbed run over a gateway-shaped model id reports a non-zero cost
marked derived with no operator-written rates; `price_strategy: none` output is
byte-identical to today's on the same fixture; an unknown model id under
`price_strategy: aws` still reports unavailable rather than guessing;
`GET /config` names the source table; the alias table resolves each documented
gateway form. Include a test that fails when the built-in table has no as-of
date.

## D. Task progress in the run list (#21) — depends on A

The hub run list shows state, verdict, phase, approach, iterations and start
time, but not how much of the plan is done.

- Add a `TASKS` column rendering `completed/total`, e.g. `5/7`, following the

- It **must** use A's hardened last-good reader, not a bare

- `ralphctl runs` gains the same column from the same counts.

# Phase 2 — make the run explain itself

## E. Steering must be readable, not just writable (#17)

The hub proxies only `POST /steering` (`cli/ui_server.py:467`) and renders only
the steer form (`app.js:352-368`) plus a warning about unconsumed entries on a
**terminal** run (`app.js:478-484`). During a live run — the one moment when
knowing whether your message landed actually matters — there is nothing.
`ralphctl steer` (`cli/main.py:2363`) only posts. So after steering you cannot
tell whether it is queued, was picked up at the last iteration boundary, or was
silently duplicated by an impatient second send.

- **Hub:** proxy `GET /steering` and render pending and applied entries on the
  run detail page — name, timestamp, state — each opening its full body in the
  existing `openTextDialog` modal (`app.js:182`): text nodes only, never
  `innerHTML`, same trust discipline as the PRD dialog.
- **CLI:** `ralphctl steer --list`, with `--json`, printing the same. The CLI
  stays the complete surface; the hub adds no capability it lacks.
- Both read the on-disk `steering/` directory when the container is gone, so a
  post-mortem can still see what was sent — the live-first/on-disk fallback the
  log and task views already use.

**Tests.** A queued entry appears in the hub within one poll and flips to
applied after the iteration boundary that consumes it; `steer --list` and the
hub agree, live and dead; the dialog renders a body containing HTML as text.

## F. Click to view details, across the run detail page (#18)

The PRD dialog (#1) and task-detail dialog (#2) proved the pattern. Extend it:
anything an operator currently leaves the hub for should be one click away.
Everything below goes through `openTextDialog` (`app.js:182`) or a structured
sibling for tabular payloads — modal `<dialog>`, text nodes only, exactly one
instance alive so the 4 s `load()` rebuild cannot stack stale copies.

Land these in order; each is independently shippable:

1. **Iteration detail.** Click an iteration in the timeline → its full log,
   phase, start/end timestamps, duration, exit reason, and the tokens and cost
   for that iteration alone. Today the timeline is a summary and the log tail is
   a separate whole-run view; there is no way to ask "what happened in
   iteration 47".
2. **Run state documents.** One click each, like the PRD already is: `notes.md`,
   `review-findings.md`, `composite-prd.md` (when the run reached a later
   approach), and the effective `job.yaml` — the persisted config as inlined at
   start, **redacted**.
3. **Artifacts and reflection.** Browse `artifacts/` in the hub; open the
   reflection report and `suggestions.diff` inline. A finished run's most
   valuable output is currently a filesystem path an operator has to go find.
4. **Fault explanation.** Click an infra-wait or failure badge → the fault
   classification, which signature matched (`engine/faults.py`), where the run
   is in the retry ladder, and how much of the outage budget is spent. The hub
   already shows infra-wait state (`app.js:464`); this is the explanation behind

5. **Cost breakdown.** Click the cost cell → per-phase and per-approach usage

CLI parity for each where one does not exist (iteration detail, run documents,
artifact listing, fault explain, cost breakdown), per SPEC.md's interaction
model: the hub is a read-mostly window onto state the CLI can already produce.

**Constraints.** Text nodes only — run dirs are outside the page's trust
boundary. Every view works from the **on-disk snapshot with the container gone**,
not only from a live API. A dialog must not hold a stale copy across a poll.

**Tests.** Browser tier per dialog: opens, shows the right payload, closes, and
does not stack across a `load()` cycle; an XSS-shaped payload in a run document
renders as text. CLI counterpart tests for each. Snapshot-mode tests with no
container.

## G. Deleting a dead run takes one command, and works from the hub (#19)

`ralphctl rm` (`cli/main.py:2481`) removes the run dir and persisted config and
reaps siblings, but **hard-fails** when a container record still exists:
`die(5, "container still exists — \`stop\` first")` (`:2484`). For a run that
already finished, that leftover container is exactly what you want gone, so the
operator's real intent always costs two commands. The hub has no delete
affordance at all.

- **`ralphctl rm --force`**: stop the container (reusing `cmd_stop`'s path so
  sibling reaping and label discipline are unchanged), then remove state, in one
  command. Plain `rm` keeps refusing, so the safe default is unchanged.
  `--force` **must still refuse a running job outright** — it is a shortcut past
  a stale container, not a way to kill live work. Aborting stays explicit.
- **Hub delete button** on the run list and run detail, for **terminal runs
  only**, behind a confirm dialog that names the run id. Disabled with the reason
  shown while a run is active, so the UI can never destroy work in flight.

Deliberately out of scope, both considered and dropped: bulk prune, and a
keep-the-artifacts delete mode (`rm` deletes the run dir wholesale; a partial
delete makes "what is in this run dir" unanswerable).

**Tests.** `rm --force` on a finished run succeeds where `rm` says `stop first`
and leaves no container, run dir, config dir or sibling; `rm --force` on a
running job exits non-zero and touches nothing; browser test for the confirm
path and for the disabled state on an active run.

# Phase 3 — the image lifecycle

## H. Build the job image, and let a job bring its own (#20)

`container/Dockerfile` is in the repo but **nothing ever builds it**. `--image`
exists on `start`/`resume`/`doctor` (`cli/main.py:3270,3333,3398,3463`),
defaulting to `RALPHD_IMAGE` or `ralphd:dev`, and `image` is a registry
`config.yaml` key (`cli/main.py:2818`) — so image *selection* is configurable
and image *production* is entirely manual. That has already cost real
observability: see fact 1. A run can quietly execute an engine that predates the
fix for the very bug you are watching for, and nothing warns.

The second half of the gap: a job whose repo needs a JDK, a specific node, or
any other toolchain cannot say so. The documented sibling-container workaround
does not help when the agent itself needs the tool in-process.

### H1. Build the default image, keyed by content hash

`start` and `resume` hash the image inputs — `container/` plus the ralphd source
installed into it — tag the result `ralphd:<hash>`, and build **only when that
tag is missing**. Repeat runs are a no-op tag lookup; a source change produces a
new tag automatically. This makes "running a stale engine" structurally
impossible instead of something an operator must remember, and it makes the
engine version in `host.json` mean something.

An explicit `--image <id>` still pins exactly what it says, with no hashing and
no build, for when you deliberately want an old engine.

### H2. Bring your own image, as a base layer

A user-supplied image is a **base**, not a finished job image: ralphd generates a
derived image that layers `ralphd-engine` and pi on top, and runs that. The
user's image only has to carry the toolchain their repo needs — they never
replicate the engine's install contract, and any ordinary dev image works. The
derived image is hash-tagged and cached the same way as the default.

### H3. Three supply points, most specific winning

- `ralphctl start --dockerfile <path>` — build that Dockerfile with its
  directory as context, then derive; persisted into `job.yaml` and replayed by
  `resume` like every other start flag.
- Per-job in `job.yaml`, so a repo carries its own build recipe and any operator
  starting that job gets the same environment.
- `image` / `dockerfile` in registry `config.yaml`, as a standing default for the
  toolchain you always use.

### H4. Constraints — read these before designing

- **`resume` must reproduce the image the run started with**, not the current
  hash of possibly-changed sources; otherwise a resume silently swaps the engine
  mid-run. Record the resolved image id in run state and prefer it.
- A failed build **fails `start` loudly, before any run state is created**. No
  half-registered run.
- Build output must be visible enough to debug a failing build without drowning
  the start path.
- `doctor` reports image **staleness** (source hash vs the tag in use), not just
  that the image exists (`cli/main.py:2970`).
- **Packaging interaction, decide and document:** a pipx-installed ralphd has no
  `container/` directory to hash. Either ship the Dockerfile as package data or
  fall back to a pinned published tag — pick one, write down why, and make the
  fallback observable rather than a silent behaviour change.
- Hashing must be stable and cheap: same tree → same tag on a second machine,
  and no full-tree walk of `.git`, `artifacts/`, or `__pycache__`.

**Tests.** Stub-docker tier: the tag is computed from content, a build is
invoked only on a cache miss, a second `start` is a tag lookup with no build, an
explicit `--image` neither hashes nor builds, a failed build aborts `start`
before run state exists, `resume` reuses the recorded image and not a fresh
hash, `--dockerfile`/`job.yaml`/`config.yaml` precedence resolves most-specific-
first, and `doctor` reports staleness. Real-build tier: build a minimal base and
assert the derived image runs `ralphd-engine` — this needs `DOCKER_BUILDKIT=0`
inside the job container (fact 5). If the real-build tier cannot run in this
environment, **say so explicitly** in the requirement's report line and mark it
operator-verified-on-host; do not let a skipped tier read as a pass.

## Cross-cutting requirements

- **No silent behaviour change to a healthy run.** A run that never hits a
  parse failure, never sets `price_strategy`, and passes `--image` explicitly
  must behave exactly as it does today. The existing 104 test modules stay green
  without modification, except where a documented contract changed
  (`status.json` gains fields; `test_issue_traceability.py` is retargeted by I).
- **Unknown is never zero, on any surface added here.** Tasks, approach
  denominators, task fractions, derived cost: absent data renders absent.
- **Text nodes only in the hub.** Every payload added by E, F and G comes from a
  run dir, which is outside the page's trust boundary.
- **Every new view works with the container gone.** The on-disk snapshot path is
  not a degraded mode, it is how a finished run is read.
- **CLI parity is a hard rule, not a nicety.** The hub adds no capability the
  CLI lacks.
- Compressed schedules/timeouts must be settable so tests never sleep for real.

## Non-goals

- No bulk prune, no partial/keep-artifacts delete (G).
- No registry-wide `price_strategy` default; no non-AWS built-in rate tables;
  no live price fetching over the network (C).
- No engine-maintained atomic mirror of `tasks.json`, and no attempt to make the
  agent write it atomically (A).
- No published image on a registry, no pipx release — H decides and documents the
  packaging interaction, it does not ship the release.
- No new `state` value, no new daemon, no remote mode, no parallel-job
  orchestration, no alternative agent runtimes. Still deferred.
- No reopening or re-litigating v0.5's closed issues.
