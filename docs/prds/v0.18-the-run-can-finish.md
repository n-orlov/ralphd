# v0.18 — the run can finish

## Goal

Since 29 August no ralphd run has completed. Six selfdev waves and four deck phases ended
`failed` at N/N approaches or died at the deadline while writing paperwork, while their own
final reviews confirmed the product green. The operator read every review verdict of every run
(118 blocking findings) and classified them: 36 product defects, all cured in the first review
cycle; 58 bookkeeping findings; 37 findings on criteria unsatisfiable by construction. Eight of
the eleven final rejecting reviews contained zero product defects. The analysis is filed as
issues #139–#147 and summarised in `docs/review-economics.md`'s v0.18 addendum (task-owned).

Three mechanisms did this. **First**, the materiality rubric every PRD since v0.15 relies on
has reached zero reviews: `findings.extract_materiality_rubric` recognises only an inline
heading, `docs/review-economics.md` told PRD authors to adopt it by reference, and every review
prompt since said "Default: every finding is blocking" (#139). **Second**, the contracts made
the run author records about its own future — a final record that must be the last commit
while later commits are mandated, a closing report that must record adjudications only the
review judging it will produce (#140, #143). **Third**, the only cure unit is a fresh approach,
which owes the whole tail again and regenerates the staleness the review objected to (#141),
and the last approach has no exit but `failed` (#142).

This wave (#139–#147):

- **A (#139)** — **the rubric is real**: by-reference adoption works, the engine's default is
  the fragment's product-blocking boundary, `ralphctl start` says which rubric review will use.
- **B (#140)** — **the harness owns the terminal record**: petitions, adjudications, steers,
  rulings, tallies and notifications are engine-written at `finishing`; a closing report is
  never faulted for events after its sha.
- **C (#141)** — **a curable rejection is a cure pass, not a replan**: cure tasks appended to
  the same approach, once, then review again.
- **D (#142)** — **the last approach cannot end `failed` on paperwork**: `verified-with-
  residuals`, or a pause for an operator ruling.
- **E (#143)** — **criteria that cannot be satisfied are refused at plan time**.
- **F (#144, #145, #146, #147)** — **ladder hygiene**: adjudicated petitions are closed by the
  engine and the adjudication review has a legal verdict; the worker's retry sees why it was
  rejected; a deadline mid-review is `unreviewed`, not `rejected`; the steer hat can skip a
  failed task.
- **G** — version 0.18.0, the roadmap block, this wave's row.
- **H** — the suite green at the final code sha, the closures, the closing report, the terminal
  summary — each defined so it can be true.

## Read this before anything else

1. **Your engine is 0.17.0.** Its rubric extractor recognises the inline `## Materiality rubric`
   heading below, so this run is the first whose review actually runs under a rubric. The cure
   pass, the last-approach pause and the harness record you build are NOT live in the loop
   that runs you — do not claim your own run exercised them; tests are the whole evidence.
2. **This run has two approaches.** Approach 2 is the operator's insurance, not your budget.
   If review rejects approach 1 on a product defect, approach 2 fixes that defect and nothing
   else. If the run ends `failed` anyway, the operator resumes by hand — so leave `main` in a
   state a human can pick up: every task pushed, notes current, no half-landed refactor.
3. **The judge stays strict on substance.** Nothing here weakens a test, a guard, or the
   review's product judgement. What changes is *what counts as blocking*: the rubric below,
   which the 0.17.0 engine will hand your reviewer verbatim.
4. **The operator may be asleep for your entire run.** Petition rather than wait for an amend;
   the mid-run adjudication is live (0.16) and the judging hats have the re-ask ladder (0.17).

## Materiality rubric

Review computes its verdict from **blocking** findings only; **residual** findings are recorded,
listed in the closing report if the report is written after them or in the engine's record
otherwise, and never reject. This section restates `docs/review-economics.md`'s rubric for this
contract and narrows nothing.

**Blocking** — any of:

- a red test at the **final code sha** (the last commit that touches anything outside
  `artifacts/reports/`, `docs/roadmap.md`, `docs/prds/README.md`);
- a requirement of this contract (A–H) not met, or a Definition-of-done predicate false;
- a false claim in a tracked artifact that changes what a reader believes **landed or its
  result**: a commit attributed for a change that shipped differently, a test result misstated,
  an issue state misreported, an invented send;
- an issue closed without evidence; a secret exposed; a weakened test or guard.

**Residual** — everything else, explicitly including: a report, roadmap block or index row that
is stale relative to commits made after it; a missing or imprecise count, sha or
cross-reference; a notification that was not sent, sent late, or not logged; a sweep or guard
record whose declared sha has a report-only gap to `HEAD` (`docs/sweep-records.md` already
permits this); a closing report that does not mention a petition, adjudication, steer or
ruling; formatting; prose infelicity; an inaccuracy in a record *about another record*. A
residual finding may be listed, never used to reject, and never turned into a task by the
reviewer.

## Petitions and late cure

The petition protocol and late-cure rule of `docs/review-economics.md` apply. Petitions go in
`artifacts/reports/v0.18-petitions.md`; the run never adjudicates its own petition and never
records an adjudication it has not received. A missed time-anchored duty (a send, a record) is
cured late and labelled late; a late cure is a residual, not a finding.

## What this PRD deliberately does not ask

These clauses sank the last ten runs and are banned from this contract, from this run's plan,
and from every success criterion the planner writes (requirement E's lint will refuse them in
future; this wave's plan_review must refuse them now):

- **No "last commit" rule.** Nothing must be "the last commit". The final guard subset runs
  at the final *code* sha; report-only commits may follow it freely.
- **No record about its own future.** No report, record or criterion states what a later
  event will be or has to record events after the sha it names ("none newly filed", "every
  petition and its adjudication", "the terminal send", a later commit's sha).
- **No per-task notification ledger.** Sends are best-effort and advisory (see below); no
  criterion mentions a send, a ledger entry or an HTTP status.
- **No sha-scoped-count rule.** Counts should name the sha they were computed at when that is
  cheap; a missing sha is residual.
- **No sweep-sha declaration rule beyond the existing guard.** Records declare `sweep-sha` as
  `docs/sweep-records.md` requires; the guard's own rules (report-only gap allowed, discharge
  pairs) are the whole obligation.
- **No audit range, no "commit exactly once", no protected-path clause.**
- **No self-referential criterion** (a task whose criterion names the sha of a later commit, or
  a row that must cite the commit writing it).

## Sequencing and planning rules

Flat plan, ~5 checkable clauses per task, wave-wide rules in the Standing Rules block once.
No task's success criteria may require a state a later task creates. Land engine code before
anything that must be green because of it. Never let a docs, report or closure task depend on
a code task. One honest attempt per task; deviations stated, never silent.

## Where work happens

`/workspace` is a checkout of this repository at `origin/main` as of launch. Commit and push per
task; `main` == `origin/main` at every task boundary.

## Pushing, and closing issues from inside the run

`--creds` places `github.env` at `$HOME/.creds/github.env` (`GITHUB_TOKEN`, `GITHUB_USER`) with
`gitconfig` and `git-credentials`; push and the REST API work with no setup.

- **Source the env file; never inline the token** (`set -a; . ~/.creds/github.env; set +a`). The
  token never appears in output, commits, reports, comments or messages.
- **Do not run `git remote -v`**; redact any quoted push output
  (`sed -E 's#https://[^@]*@#https://***@#g'`).
- **Verify every closure with a fresh `GET`.** Never write a closing keyword + issue number in a
  commit message unless that commit closes that issue.

## Telling the operator what is happening

The `telegram-notify` skill is placed and the run is on `--network host`; the notifier is
`http://100.71.162.65:8090`. Read `~/.pi/agent/skills/telegram-notify/SKILL.md` before your
first send. The operator is AFK and reading Telegram, not the log.

Send, best-effort: plan accepted; each approach rejection or cure; each sweep with its log as a
file; each closure with its URL; the terminal summary. Sends are advisory: **a failed or missed
send is never a task failure, never a criterion, never a finding above residual.** Do not keep
a ledger file; the engine record you build in B is where sends belong in future.

# The requirements

## A — the rubric is real (#139)

1. **By-reference adoption works.** The contract text handed to review (the composite PRD path
   in `_write_composite_prd` and the plain-PRD path) inlines the `## Materiality rubric` section
   of a document the PRD names as its contract fragment — a line of the form "the materiality
   rubric … of `docs/review-economics.md` appl(y|ies)" or an explicit
   `<!-- rubric: docs/review-economics.md -->` marker, resolved relative to the workspace. The
   inline heading path stays. Pinned by tests for: inline, by-reference (prose form and marker
   form), both present (inline wins), reference to a missing file (falls to A.2 with a `log`
   event naming the path).
2. **The engine's default is the fragment's boundary.** When no rubric is found,
   `materiality_rubric_context` hands review the product-blocking/residual text of
   `docs/review-economics.md` (kept in the source tree as the single copy, e.g.
   `findings.DEFAULT_RUBRIC`) instead of `ALL_BLOCKING_DEFAULT_NOTICE`, and says so ("no rubric
   supplied; the engine default applies"). `review.md`'s "never invent your own boundary"
   sentence stays; its all-blocking description goes. `docs/review-economics.md` § "Using this
   fragment" and `docs/prds/README.md` say which forms work and that all-blocking is no longer
   a fallback.
3. **`ralphctl start` says which rubric applies.** The start output (and `doctor` for a
   `--prd` it can read) prints one line: `rubric: inline` / `rubric: by reference
   (<path>)` / `rubric: engine default`, and warns when a referenced file does not resolve.

## B — the harness owns the terminal record (#140)

1. **`run-record.md` + `run-record.json`** are written by the engine into the run's
   `artifacts/` at every entry to `finishing` (and rewritten on later terminal transitions):
   approach history (each review/verdict-gate verdict with its blocking and residual findings
   and the archived approach dir), every petition with its adjudication from
   `petition-adjudications.json`, every steer consumed and every operator ruling found in
   `/config/amendments`, the task tally per approach, `iterationsUsed`/tokens/cost from
   `status.json`, and the notification log (B.3). `ralphctl docs <run>` and `ralphctl
   artifacts <run>` surface both; the web hub links them.
2. **Review is told what the engine owns.** `review.md` and the contract context state that
   petition/adjudication accounting, steer and ruling history, approach history, terminal
   tallies and notification accounting are the engine's record, and that a closing report is
   never faulted for omitting or predating them; a closing report's obligations are: what
   shipped per requirement, its evidence (commit, test node ids), and the residuals it knows
   of, at the code sha it names. Pinned lexically.
3. **Sends are engine-recorded.** A `notify` hat tool (the `hat_tools` spool shape, available to
   worker and steer) POSTs to the configured notifier URL from the engine side and records
   `{ts, endpoint, textSha256, httpStatus}` as a `notification.sent` event and in the run
   record. The `telegram-notify` skill's SKILL.md tells the agent to prefer the tool when
   present and is otherwise unchanged. A failed send is an event, never a task failure.
4. **`docs/review-economics.md` gains a v0.18 addendum** stating the banned clause shapes of
   this PRD's "What this PRD deliberately does not ask" section and that the final guard subset
   is "at the final code sha", never "the last commit".

## C — a curable rejection is a cure pass (#141)

1. **A new declared edge `review -> cure`** in `engine/transitions.py` (both variants, mermaid
   included): taken when review's verdict is `rejected`, every blocking finding has
   `curable: true`, and `curePasses[approach] == 0`. The engine appends one cure task per
   blocking finding to the current approach's `tasks.json` (title from the finding, criteria =
   the finding's `clause` and `evidence` bounded to ≤5 clauses, `origin: "review-cure"`),
   increments `curePasses` in status.json (surviving resume), emits `approach.cure_pass`, and
   routes to worker. When every cure task is validated the ordinary `COMPLETE -> review`
   path runs again.
2. **Bounded.** A second `rejected` in the same approach takes today's replan edge
   (`rejected_approach_left`) or requirement D on the last approach. `rejected_incurable` keeps
   precedence when every blocking finding is incurable.
3. **Pinned** at the in-process `LoopSupervisor` tier (cure tasks appended, worker routed,
   second rejection replans, resume mid-cure) and by one black-box e2e with a stub `pi` whose
   review rejects once with curable findings then verifies.

## D — the last approach cannot end `failed` on paperwork (#142)

1. On the final approach (`approach == max_approaches`), a `rejected` review whose blocking
   findings are all `curable: true`: if C's cure pass is available, take it; otherwise take a
   new declared edge `review -> paused` named `rejected_last_approach`, generalising
   `_pause_and_escalate_incurable_rejection`: `operator_escalation` event with
   `reason: rejected_last_approach`, status `paused`, a notification via B.3 if configured, and
   `resume` after an `amend`/`--waive` re-runs review over the same approach (the archive is
   not written until the run actually ends).
2. A `rejected` review with any `curable: false` blocking finding on the last approach keeps
   `rejected_no_approach_left` → `failed`.
3. **`verdict: verified-with-residuals`** is recorded (status.json, `ralphctl status`, hub)
   when review verifies with one or more residual findings in the channel; `verified` stays for
   a clean channel. `state` is `succeeded` in both cases.
4. Pinned at the in-process tier for all three outcomes and for `resume` from `paused`.

## E — criteria that cannot be satisfied are refused (#143)

1. **A seventh lint** in `plan_ingestion.lint_proposal()` flags, in `successCriteria`, the
   shapes this PRD bans: a reference to a later/final/last commit or its sha; a predeclared
   event state ("none newly filed", "no approach rejected", "all petitions REFUTED"); a record
   that must cite the commit that writes it; a git range that must be empty; "exactly once"
   commit counts; a notification/HTTP-status clause. Scope cues to the clause (the #86 lesson);
   fixtures verbatim from v0.14 a3, v0.15 a2, v0.17 a3/a4, deck-3h/3i/spike as must-catch, and
   must-pass siblings that name a *past* sha, an existing artifact, or "the code sha this task
   lands".
2. The refusal goes through the existing plan re-ask ladder naming the clause and a satisfiable
   form; `plan_review.md` carries the same list as a checklist item.
3. Pinned by unit fixtures in both directions and one ingestion-level test.

## F — ladder hygiene (#144, #145, #146, #147)

1. **Adjudicated petitions are closed by the engine (#144).** A petition present in
   `petition-adjudications.json` is rendered to review as history, never as open or re-filed;
   `review.md:98-101`'s re-file rule applies only to a *new* filing against an adjudicated
   obligation. The mid-run adjudication review (`midRunAdjudication: true`) gets a legal
   verdict value `adjudicated` (or `verdict` optional for that episode) so it stops faulting
   3/3 against the review contract; the safe default at exhaustion is unchanged.
2. **The worker's retry sees the rejection (#145).** A task dispatched at
   `validationAttempts > 0` carries `validationNotes` verbatim in its prompt block under a
   heading "Why the previous attempt was rejected" with the attempt count; `worker.md` says to
   address it or petition. Pinned lexically at the in-process tier.
3. **A deadline mid-review is `unreviewed` (#146).** An interrupted or timed-out review
   iteration (ordinary or `_maybe_grace_review`) ends the run `verdict: unreviewed`,
   `reason: deadline during review`, never logs `review rejected`, and a `resume` with a fresh
   window re-runs review over the same approach. Pinned at the in-process tier.
4. **The steer hat can skip a failed task (#147).** `task-update` to `skipped` from `failed`
   carries a `justification` (the steer's stated reason) to the transition check and into the
   task's `notes`, as the worker channel does. Pinned at the `hat_tools` unit tier.

# Non-negotiables

1. A non-zero pytest exit at the final code sha is RED; petition once per obligation, never
   waive yourself.
2. Never weaken a test, guard or the review prompt's product strictness to force green.
   Findings may be classified by the rubric, never dropped.
3. The run never grants itself a severity, a curability, a petition outcome or a criteria
   amendment; the PRD and `/config` are amendable by no one inside the container.
4. Closures carry evidence, fresh-`GET` verified; no closing keyword + issue number in a commit
   message unless that commit closes that issue.
5. `main` == `origin/main`, clean tree, at every task boundary.
6. Secrets never appear anywhere.
7. Flat plan, sequencing rule, bounded criteria, none of the banned clause shapes.

# Definition of done — predicates, each owned by a named task

1. A PRD adopting the rubric by reference (prose or marker) yields a review prompt containing
   that rubric verbatim; with none, the engine default text; inline wins over reference;
   `ralphctl start` prints the rubric line; the all-blocking notice is gone (#139).
2. `run-record.md`/`.json` exist after `finishing` with approach history, petitions +
   adjudications, steers, rulings, tallies, usage and the notification log; `ralphctl docs`
   shows them; `review.md` states the engine's ownership; the `notify` tool records a
   `notification.sent` event (#140).
3. A curable rejection appends cure tasks to the same approach once and re-reviews after they
   validate; a second rejection replans; `curePasses` survives resume; the FSM doc shows the
   edge (#141).
4. On the last approach, all-curable rejection → cure pass or `paused` with
   `rejected_last_approach`; `resume` re-runs review; incurable → `failed`;
   `verified-with-residuals` recorded when residuals exist (#142).
5. The seventh lint catches the must-catch fixtures and passes the must-pass siblings through
   the re-ask ladder; `plan_review.md` carries the checklist (#143).
6. Adjudicated petitions render as history; the adjudication episode has a legal verdict and
   no longer faults the review contract (#144).
7. The worker prompt at `validationAttempts > 0` carries `validationNotes` under the named
   heading (#145).
8. A timed-out review ends `unreviewed`, never `rejected`; resume re-reviews (#146).
9. Steer `task-update` `failed → skipped` applies with its justification in `notes` (#147).
10. Version `0.18.0` in both files; roadmap block; the row per the snapshot convention;
    `LAUNCH_SHA` current (G).
11. #139–#147 closed with fresh-`GET`-verified evidence or the cut disclosed; all six lanes
    green at the final code sha and recorded; the closing report written once after the lanes;
    one terminal summary sent (H).
