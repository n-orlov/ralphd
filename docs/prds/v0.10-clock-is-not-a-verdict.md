# ralphd v0.10 — the clock is not a verdict

## Goal

Your predecessor finished its work and the harness threw the result away.

`selfdev-v09-fsm-loop` verified its last task at `2026-08-26T06:52:20Z`, emitted
`signal: COMPLETE`, and entered `review` on approach 3 with 20 of 23 tasks
completed-and-verified and every commit pushed. The job deadline fired **3m34s
later**, mid-review. The review hat never got to speak. The harness read its
silence as a rejection, logged `review rejected approach 3`, archived the
approach, wrote a composite PRD for a fourth, spent ~$1.11 planning it, and
landed the run `state: failed`, `verdict: unverified`.

Nothing was wrong with the work. What was wrong is that an *absence* of judgement
was scored as a judgement against.

This wave fixes that, and it fixes it in the vocabulary your predecessor built:
`engine/transitions.py`'s `TABLE` already declares that `planning` may retry in
place when an infrastructure event kills it —

```python
"planning": (
    # ledger guard 1: an instant/infra failure retries planning in
    # place without costing the approach (loop.py:1978-1985).
    T("planning", "instant_failure_streak"),
    ...
```

— and `review` has no such row. Four declared edges out of `review`
(`steering_pending_at_verified`, `verified`, `rejected_approach_left`,
`rejected_no_approach_left`) and not one of them means *the iteration was cut
short before it could judge*. The bug is a missing row in a table, which is
exactly the kind of bug v0.9 existed to make visible.

The principle, stated once so every requirement below can be checked against it:

> **An interrupted iteration is not a verdict.** Not a rejection, not a
> completion, not a failure of the work. Silence caused by the harness is
> attributable to the harness.

This project has ruled that way twice already and both rulings hold today: task
117 made `classify_fault` decide bare-aborted-after-traffic on *shape*, not on
error text, and the stagnation guard excludes non-work faults so three
consecutive infra deaths cannot fail an approach
(`tests/test_stagnation_excludes_nonwork_faults.py`). `_review_verdict` never got
the memo. Neither did the finishing tail: the same deadline that ended the review
also cut the `reflect` iteration short, so the wave produced no reflection report
at all — `artifacts/reflection/` holds only `FAILED.md`.

The rest of the wave is your predecessor's own ticketed debt, which it deferred
honestly under operator steering rather than half-doing: the conformance ledger,
two documentation gaps, and a test script that disarms the very isolation it
depends on. One more defect joins them, found while repairing the damage the
first one caused: the legacy vigilant-sidecar migration silently discards a whole
approach's verifications once the approach counter has moved on (requirement J).

## A. An interrupted review is not a rejection (#72)

Add the missing edges to `transitions.TABLE`'s `review` entry and implement them.
At minimum:

- an edge that keeps the run in `review` when the iteration was cut short and
  there is budget and wall clock to ask again — the same shape as `planning`'s
  `instant_failure_streak` and `worker`'s `no_verdict_yet`, and it must not cost
  the approach;
- an edge to `finishing` for the case where there is *no* time or budget left to
  re-ask, which does **not** archive the approach, does **not** emit `review
  rejected approach N`, and does not write a composite PRD for a successor
  approach that will never run.

Guard names are yours to choose, but they must say which condition they mean;
`review_interrupted` and `review_unjudged_at_budget_end` are serviceable. Both
must appear in `guard_names("review", vigilant)` for **both** table variants, and
the existing four edges must keep their exact current names and meanings.

`_review_verdict` keeps its current contract-payload semantics for every case
where the hat actually replied — a malformed or absent payload from an iteration
that *ran to completion* is still an ordinary non-verified verdict, and still
must not crash the run (fact 7). The new behaviour keys on the iteration having
been interrupted, from `IterationResult` (fact 9), not on the payload being
missing.

Then **audit the same shape everywhere else a hat's reply is scored**:
`_step_verify`, `_step_planning`, `_step_worker` and the reflect path. For each,
state in notes whether an interrupted iteration can currently be read as a
substantive outcome, and fix the ones where it can. `planning` already has its
row; `verify` and `worker` need checking rather than assuming.

Tests, and this is the bar: a test that drives a real `review` iteration to an
interrupt and asserts the approach is **not** archived, no `review rejected`
event is emitted, and the approach counter does not advance — plus a mutation
test in the shape v0.9 used throughout, i.e. one that makes the fix stop
discriminating and proves the test then fails. Reproduce v0.9's exact sequence
(COMPLETE, then review, then interrupt) as a named regression, and cite run
`selfdev-v09-fsm-loop` iteration 183 in the test's docstring.

## B. A run that has earned `COMPLETE` does not lose it to the clock (#72)

Requirement A stops the approach being burned. This requirement is about the
terminal record.

When every task in the record is `completed` and verified, `COMPLETE` has been
emitted and honoured, and the only thing that did not happen is the final review
returning a verdict, the run's terminal state must not read as though the work
failed. Decide what it *should* read as — and the operator's ruling on the one
point that is not yours to choose:

> A run that never obtained a review verdict must not claim `verified`. Whatever
> you land, `verdict: verified` stays something only the review hat can grant.

So the space is: a distinct verdict value, or a distinct terminal state, or the
existing `failed`/`unverified` plus a mandatory, machine-readable `reason` that
names the deadline and the honoured `COMPLETE`. Pick one, implement it, and write
down what you rejected and why. Whatever you pick must be visible to
`ralphctl status`, in `status.json`, and in the `docs/prds/README.md` row
convention — a human reading the index must be able to tell "the work failed"
from "the clock beat the verdict".

`_unconsumed_steering_patch`'s existing precedent is the model to follow: a
terminal write that names the thing that was stranded, so the condition is
loudly discoverable from the record rather than only from the transcript.

## C. The finishing tail gets time it cannot be robbed of (#72)

`reflect` is the run's own account of itself and it is the first thing the
deadline eats, because the deadline that ends the work is the same deadline that
bounds the unwind. v0.9 lost its reflection entirely this way (facts 10, 11).

Decide and implement **one** of: reserve a tail budget out of `job_timeout_s` so
`finishing`/`reflect` always has room; extend the deadline for the unwind the way
infra waits already extend both deadlines (`_account_infra_wait`, and note that
mechanism's own reasoning — "an outage must not eat the job's working time" — is
the same argument); or give the reflect iteration its own independent bound.
Write down the two you rejected and why.

Constraints: whatever you choose must not let a run extend itself indefinitely,
must keep `job_timeout_s`'s documented meaning honest in `docs/cli.md` and
`SPEC.md`, and must be asserted by a test that drives a run to its deadline with
reflect enabled and shows the report gets written.

## J. A resumed run dir does not lose an approach's verifications (#75)

`RunDir.migrate_legacy_vigilant_verified()` (`engine/state.py:3757-3795`) folds
the pre-0.9 `vigilant-verified.json` sidecar into the task record and then
**unlinks the sidecar**. It matches the sidecar's approach-namespaced entries
(`"<approach>:<taskId>"`) against `current_approach()` — `status.json`'s
*current* `approach`, not the approach each task was verified under. Any run dir
whose approach counter has moved on therefore matches nothing, demotes every
`completed` task to `awaiting-validation`, and destroys the evidence on the way
out. It is documented as one-way and it is: the loss is unrecoverable.

This is requirement A's bug wearing a second hat. #72 advances the approach
counter on an interrupted review; #75 then erases the verifications the moment an
engine next starts against that run dir. Observed on `selfdev-v09-fsm-loop`: 20
tasks verified under approach 3, `status.json.approach` sitting at 4, and 20
consecutive `task oldStatus=None newStatus=awaiting-validation` events in one
second, followed by the sidecar's deletion. The task record was recovered from
`approaches/03/tasks.json`; the sidecar was not.

Fix shape: fold **every** approach's entries rather than one approach's — the
archived per-approach records already carry that structure — or resolve each task
against the approach it was completed under. And do not unlink the sidecar until
the fold is known to have preserved what it names: today, a migration that
legitimately finds nothing is indistinguishable from one that matched nothing
because it asked the wrong question. Pin both halves with tests, including the
approach-advanced case that currently loses everything.

## Cross-cutting requirements

**The test-tier rule. This is the rule your predecessor lost the most time to;
it is not advisory.**

- `pytest` gets `-m "not browser and not docker"` **every single time**, except
  inside the one task that records the tiers. A bare `tests/` path argument is
  not a filter — it is the whole suite plus both slow tiers, and it does not fit
  in an iteration.
- Bound and background every sweep: `nohup timeout 2400 … > file 2>&1 &`, then
  poll the file. Never pipe a long pytest through `tail -1` — even on success
  that throws away the failure list, which is the only part you needed.
- Per commit: the modules covering what you changed, plus the drift lane. That
  is seconds.
- **A bound that fires is not a test result.** If `timeout` kills your suite you
  have learned only that the target set is too big, so narrow the target set.
  Re-running the identical command is the one response guaranteed not to help.
- **Killing pytest does not kill the browser.** `@playwright/cli`'s `cliDaemon`
  and its Chrome tree are not children of the pytest process; they reparent to
  PID 1 and keep running. v0.9 leaked a nine-process, ~1.2 GB Chrome tree that
  outlived its pytest by 51 minutes, three separate times, on a host carrying
  other live runs. After any tier that touches the browser: check for a
  `cliDaemon` at ppid 1, kill it by name, and re-check that it is gone. The same
  applies to a leaked `ralphctl ui` server.
- The docker tier cleans up by **exact tag and exact container name, never by
  label query or wildcard**, because this host carries other people's live runs.
  Never run `docker prune`.

**Poll with sleeps you can survive.** v0.9's last iteration sat in `sleep 900`
polling a sweep that had already finished, and would have woken with 84 minutes
left on the clock to discover a red result. Poll in increments that leave you
time to react.

**Pacing.** Wall clock, not iterations, has been the binding constraint in every
one of the last four waves. v0.9 used 126 charged iterations of 500 and ran out
of *time*. Do the mechanical, ship-shaped work (requirement I) early; leave the
tail for the tail.
