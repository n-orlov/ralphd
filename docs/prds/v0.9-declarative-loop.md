# ralphd v0.9 — the loop's rules become data, and only the harness writes state

## Goal

Eight waves have taught this loop roughly twenty lessons, and every one of them
lives as a branch inside one 2886-line function. `_run_job_core` is now a
correct, well-commented, untestable-in-outline artefact: each `if` is a real
incident (a `pkill` that ended a 9h36m run, a `COMPLETE` that was not earned, a
resume that re-verified nothing, an operator ruling that could not reach review),
and nothing states the machine those branches add up to. You cannot read the
transition space, you cannot assert it, and adding a hat means surgery.

This wave makes the machine explicit and moves the authority for task state from
the agent to the harness. Two changes, one principle:

1. **The transition space becomes a declared table.** States, legal transitions
   and per-hat response schemas as a data structure the engine executes and the
   tests validate against. Vigilant and non-vigilant become two variants of one
   table rather than two implicit paths through one function.
2. **An iteration stops writing its own report card.** Today the agent edits
   `tasks.json` and the engine reads it back and tries to catch lies — the
   `honoured_complete` cross-check, the criteria fingerprints, the
   `vigilant-verified.json` sidecar and the stale-read cache all exist because
   the thing being graded holds the pen. Under this wave the agent *reports*
   through a schema and the **harness** applies every state change.

The organising principle, and the operator's ruling on the one point where the
design was still open:

> **Task state changes only at step transitions, and only the harness makes
> them.** The router selects a task, and the harness sets `in-progress` before
> the worker ever sees it. The worker reports, and the harness sets
> `awaiting-validation`. In-step there is no task-state change at all — the log
> stream is the only live state.

That is stronger than "the agent should not lie about status": it removes the
sentence in which a lie could be written. It also retires the 0.25 s
`tasks.json` poll, and it means every status value in the run has a transition
edge behind it that a test can name.

Requirement A is the same principle applied to the boundary the last wave left
open: an iteration can currently reach the engine's own control API over
loopback and rewrite the prompt of the hat that judges it. Harness-owned task
state is worth little while that is true, so A lands first.

Every mechanism named below was verified against `deee207` while this PRD was
written, on the operator's host, and the facts section says which are
measurements and which are judgements.

    `conftest.py` now pre-binds `sys.modules["tests"]` to a namespace-style module

    imported* the decoy, and asserts full collection under the strongest form.

    given, so an invocation that collects nothing under this repo never loads the

    exactly such an invocation (it runs an out-of-tree probe), and an installed
    `tests` package is on `sys.path` for *every* invocation regardless of target.

    passes `-p tests_package_pin`. **Do not fold it back into the conftest** — the

    only for the invocation it was written for.

    Design the table so both are cheap to add — that is the test of whether the

19. **#67 — a fresh `$HOME` used to un-install Python for the child, and the fix
    is a helper you must route new spawns through.** 19 modules launch the engine
    with `stub_env={"HOME": <tmp>}`, deliberately: a virgin `$HOME` *is* the
    subject of the creds / skills / prompts / llm-config tests. On a `pip install
    --user -e .` layout that override also hides user site-packages, because
    `site` derives `$HOME/.local/lib/pythonX.Y/site-packages` from `HOME` at
    interpreter start. The child died with `ModuleNotFoundError: No module named
    'ralphd'` before binding a port — and **the message was invisible**, because
    the engine's stdout is a `PIPE` nothing reads until the test is already
    failing. The symptom was `TimeoutError: engine API never came up`, 15 seconds
    later, in a fixture, with no mention of imports. Measured before the fix:
    `tests/test_cli_creds_crud.py` → `1 passed, 7 errors in 105.37s`; after →
    `8 passed in 5.71s`. **No virtualenv hides this one** — unlike #65 it
    reproduces identically under an interpreter with the scripts beside it, which
    is what makes it a separate defect rather than a symptom of #65.

    The fix is `tests/conftest.py:with_ralphd_importable(env)`, and it sets **two**
    variables because only one of them is obvious:

    - `PYTHONUSERBASE` is the load-bearing half. `HOME` does not merely hide
      `ralphd`; it hides everything installed beside it — `uvicorn`, `fastapi`,
      `pyyaml`. Setting only `PYTHONPATH=<repo>/src` moves the failure from
      `import ralphd` in the console-script wrapper to `import uvicorn` at
      `engine/main.py:13`: the same silent 15-second timeout, one line further in.
    - `PYTHONPATH=<repo>/src`, *prepended*, decides **which** build the child
      imports — this checkout, not whatever wheel sits in site-packages. Prepended
      rather than assigned, because `scripts/host_like_pytest.sh` runs the suite
      with a decoy `tests` package on `$PYTHONPATH` and clobbering it would
      quietly disarm that scenario.

    Every place the suite spawns this repo's code routes its **merged** env
    through the helper, after `stub_env`: `LiveRun` and `LiveRun.ralphctl`
    (`tests/conftest.py`), `EngineProc` (`tests/test_e2e.py`),
    `test_config_overlay.py`'s fixture, and `Ctl.run` (`tests/test_cli_docker.py`)
    — `ralphctl` is the same package behind a second console script, so a `HOME`
    handed to *it* fails the same way. **If this wave adds a spawn point, route it
    through the helper too**, and assert importability and `$HOME` isolation as one
    pair: a "fix" that restored the import by leaking the real `$HOME` back in
    would trade this defect for a worse one, with 19 modules reading the
    operator's own `~/.pi`. `tests/test_engine_child_import_path.py` pins both

# Phase 2 — the table, and who holds the pen

## B. The transition space is a declared table the engine executes (#60 pillar 2)

States, legal transitions, and the predicates that choose among them, as an
internal data structure — not operator-editable, not a config file. Vigilant and
non-vigilant are two variants of one table. `_run_job_core`'s control flow is
replaced, not wrapped: #60's decision is "replace the loop core outright" and
there is to be no legacy dual path.

The transitions to express, at minimum: entry at `planning`;
`planning → worker`; `worker → worker | verify` (vigilant) or
`worker → worker | review` (non-vigilant); `verify → worker | worker(next)`;
`review → worker | replan | finishing`; the approach boundary as a transition
with a guard; `finishing` as a non-terminal run state (fact 11); and the reflect
unwind after it.

Acceptance:

- One module holds the table and nothing else holds transition logic. A test
  asserts the engine cannot take a transition the table does not list — by
  driving an illegal one and seeing it refused, not by reading the table back.
- Every state's legal successors are enumerable and rendered somewhere a human
  reads: `docs/architecture.md` gets the table, generated from or checked
  against the code, with a mutation case.
- Adding a hypothetical hat is a table entry plus a prompt plus a schema, with
  **no edit to the transition executor**. Prove it: add a trivial no-op hat in a
  test, drive it, and assert the executor was untouched. This is the property
  that makes v0.10's peer gates cheap, and it is the only evidence that the
  table is a design rather than a lookup wrapped around the old branches.
- The two modes differ **only** by which table variant is selected — asserted, so
  a later vigilant-only fix cannot silently fork the paths again.
- Resume reconstructs FSM position from disk and continues legally. A run killed
  in each state resumes without repeating completed work and without skipping a
  gate; `ralphctl repair` likewise.
- Router calls (requirement E) and contract re-prompts (requirement C) are
  **not** charged as work iterations, and a test pins that they are not.

## C. A hat reports; the harness writes (#60 pillar 1)

Each hat has a response contract: a per-hat JSON schema its final output must
match, which the harness parses and applies. `COMPLETE`/`VERIFIED` sentinel
strings are replaced by schema fields. Fact 4 is the constraint: nothing enforces
the schema for you, so validation and re-prompt are the mechanism.

Per-hat payload channel, as #60 decided: small verdicts (worker, verify) inline
in the final output; the plan — and plausibly review findings — **file-borne**,
the hat drafting `plan-proposal.json` in its writable scratch area and its final
output carrying a pointer and a summary. The harness treats the proposal as
untrusted input: schema validation, then semantic lint, then ingestion.

Acceptance:

- Every hat's schema is declared beside its table entry, and a test enumerates
  hats-with-schemas against the table so a new hat cannot ship without one.
- The harness applies every state change. `tasks.json` is written by exactly one
  code path, and a test asserts no other writer exists — the check has to be
  structural (an audit of writers) rather than a promise in a docstring.
- **Planner contract**: planner-chosen ids survive (`"001"`…, human-meaningful and
  referenced by notes and prompts); the plan schema has **no status field**; the
  harness initialises every ingested task to `pending`. Assert that a proposal
  carrying a status is rejected rather than honoured.
- **Semantic lint on ingestion**: `dependsOn` refs resolve, no cycles, no
  duplicate ids, no empty or boilerplate `successCriteria`. Failure re-prompts
  the planner with the specific error, under the same N-then-agent-fault policy
  as any contract violation. Structural checks only — plan *quality* is not the
  lint's business.
- **The lint includes requirement H's rule**: a task whose criteria depend on
  this run's own terminal state is rejected at ingestion, naming the task and the
  criterion.
- A malformed, truncated or absent payload is an ordinary case: the harness
  re-prompts with the validation error, N times, then scores an **agent-fault**
  iteration against the budget and the loop continues per the table. Test all
  three of malformed / absent / valid-JSON-wrong-shape.
- **Notes are hybrid.** Only task *state* is harness-owned. The
  `## Standing rules` block becomes harness-owned too — supplied once via the
  planner's contract, pinned and re-injected so it mechanically survives a
  worker rewrite. The rest of `notes.md` stays a free workspace file the agents
  write directly. Assert the standing-rules block survives a worker that
  overwrites the whole file.
- The same proposal mechanism serves **replanning** at an approach boundary.
- `review.md:46`'s distrust rule is preserved and re-stated in terms of the
  contract: a report is a claim, and a claim about a file the run can write is
  still worth less than the file. Say why the contract makes this stronger
  rather than redundant.

## D. Task state is unwritable by the agent where the kernel can say so (#60 pillar 1)

The operator's decision: **root-owned when privsep is in force, contract-only
otherwise**, with the tests passing in both. Fact 7 is why there is no third
option: the engine's effective uid is `agent` deliberately, and `separated()` is
false in the test suite by design.

Acceptance:

- Under privsep, `tasks.json` (and whatever else holds authoritative task state)
  is not writable by the agent uid, and the engine raises its effective uid only
  for the write. Asserted in the docker tier, where a real job container is the
  only place the boundary exists.
- Without privsep the same code runs and the same tests pass, with enforcement
  documented as contract-only and one warning logged — the existing
  degrade-don't-fail discipline, not a second code path.
- The run dir stays usable to the operator: `ralphctl rm`, `ralphctl repair`,
  `ralphctl tasks`, the hub's readers and `DELETE /api/runs/<id>` all still work
  against a run whose task state is root-owned. **Test the deletion path
  specifically** — a root-owned file inside a user-owned directory is unlinkable,
  but that is a claim, and it is the one that would strand every run dir on the
  operator's disk if it were wrong.
- SPEC and `docs/architecture.md` state plainly that hand-editing a live run's
  task record is no longer available, and name the channel that replaces it —
  today `ralphctl steer`, in v0.10 the steering task.

## E. Transitions are deterministic first, and the router answers one question (#60 pillar 2)

The harness decides wherever the table makes it unambiguous — one legal
transition, or an obvious next pending task. Only a genuine choice reaches a
model, and then it is an extremely constrained step: one question, one JSON
object (`{"next_step": "worker", "task_id": "123"}`), validated against both the
table's legal transitions and the schema.

Acceptance:

- A test enumerates the states in which the harness must decide without a model,
  and asserts no router call happens in any of them. The router's *absence* is
  the property; measure it by counting calls, not by inspecting prompts.
- An invalid router answer re-prompts with the validation error, and the loop
  never accepts an illegal transition even after N failures — it falls back to a
  declared deterministic choice rather than proceeding on a guess. Say in the
  table what that fallback is for each ambiguous state.
- Router calls are accounted separately: visible in `usage.byPhase` (or its
  successor) and **not** charged as work iterations. Their cost is reported, not
  hidden.
- The router's model is configurable with a shipped default, through the existing
  `model_overrides` mechanism. **Do not** build pillar 4's per-hat model roles
  here (Non-goals) — one new key, not a config rewrite.
- Latency has a budget: a router call that hangs cannot stall the loop, and the
  timeout has a test.

## F. Task status is a mini-FSM the harness advances at transitions (#60 pillar 3)

The operator's ruling is the specification:

> in progress should be set once router selected task, before passing on to
> worker. once worker completes and reports, harness sets "pending validation".
> etc etc. tasks state change is okay to happen during step transition only.
> in-step — logs stream is the only live state.

Target lifecycle, from #60:

```
vigilant:     pending → in-progress → awaiting-validation → validated
                            ▲               │ verify
                            └── validation-failed ◄┘
non-vigilant: pending → in-progress → completed
either:       failed / skipped (terminal dead), harness-derived blocked
```

Acceptance:

- Every status change happens at a transition, made by the harness. A test
  asserts that no status changes while a hat is executing — drive a long hat and
  sample the record.
- The declared status transition table rejects illegal moves: an illegal
  transition proposed in a hat's output is a contract violation, handled as
  requirement C handles any other.
- `awaiting-validation` replaces `completed` as the worker's claim state in
  vigilant mode; `validated` is the verifier-granted terminal; `completed` stays
  the non-vigilant terminal. Every reader in fact 8 moves with it: counts
  mapping, actionable/completion sets, prompts, `ralphctl status`, `ralphctl
  tasks`, the hub's labels and the task dialog.
- **The `vigilant-verified.json` sidecar is folded into the task record** and its
  approach-namespacing property (#29) is preserved by the new representation —
  with a test that a replan's renumbered task 001 is not read as approach 1's
  validated task 001. That bug cost a whole wave's per-task verification once;
  it does not get to recur through a refactor.
- **Dead dependencies are harness-derived**: when a dependency reaches `failed`
  or `skipped`, the harness marks dependents rather than the worker prompt asking
  an agent to notice. Dead subtrees are visible in `ralphctl tasks` and the hub.
- Per-task validation status is visible on every surface for the first time —
  `awaiting-validation` vs `validated` vs `blocked` — which is the UI gap #60
  names.
- **In-step liveness is the log stream, and it must be as good as what it
  replaces.** `_poll_task_changes`' 0.25 s poll retires; before it does, pin what
  the hub loses and show the log stream covers it. The run detail must not go
  blank for the length of a worker iteration.

## A note on size, for whoever plans this

This is a rewrite of the most load-bearing code in the project, and the honest
risk is not that the table comes out wrong — it is that the table comes out
right and takes a lesson with it. So the order is not negotiable in two places:

**A first.** Every claim about who can write what depends on it, it is small, and
it does not get cheaper later. The other half of this pairing — the harness every
suite figure you quote depends on — is already done and closed (facts 15, 16,
19), which is the only reason this wave gets to start on the table directly.

**G is not a closing task.** The conformance ledger is how you rewrite, not how
you report having rewritten. Build it before you delete anything: read
`_run_job_core` end to end, write the ledger's rows from the comments, and let
the table's shape fall out of the guards it has to express. A ledger written
afterwards is a summary; written first it is a specification, and it is the only
artefact that can tell you the rewrite is finished.

Then B and C together (the table is not testable without the contract, and the
contract has nowhere to land without the table), D and F behind them, E last of
the core — the router is the smallest piece and the easiest to get wrong in a way
tests catch cheaply. H and I are small once F exists; both are predicates on
transitions that will already be there.

Two traps worth naming. **Do not port the branches.** A table whose predicates
are the old `if` conditions in a dict is the old function with extra indirection,
and requirement B's "add a hat without touching the executor" test is what
catches it. And **do not let the contract become a second tasks.json** — the
worker's report is a claim about what it did, not a patch to apply; the harness
decides what that claim means for the record, which is the whole point of
`review.md:46` surviving this wave.

You are on `balanced`, so worker iterations are cheaper and less patient than
planning ones. The reading in this wave is genuinely large — `loop.py` is 2886
lines and `state.py` is 3543 — so use the facts above, `grep -n` and `sed -n`
rather than whole-module reads, and spend the strong tier where it belongs:
planning, the ledger, and review.
