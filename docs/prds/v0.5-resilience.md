# ralphd v0.5 — session resilience, self-recovery, and the backlog

## Goal

Make a ralphd job survive its environment. Today a four-minute DNS wobble can
destroy half a job's approaches, a container that dies takes its run's
observability with it, and the documented way for an agent to wait for
completion returns "finished" for a run that is very much alive. Close all
thirteen filed issues (#1–#13, minus the closed #12), with the resilience and
self-recovery set landing **first and independently**.

The organising principle for the resilience half: **a transient LLM-endpoint
fault must cost the job nothing but wall-clock time, and a broken
configuration must still fail fast.** Those two pull in opposite directions;
requirement A/B below is mostly about keeping both.

# Phase 1 — resilience and self-recovery

Requirements A–I. Land them in this order; A and B are the load-bearing ones
and everything else in this phase is either a prerequisite or fallout.

## A. Classify in-band LLM errors as faults at all (#11, blocks everything)

`classify_fault()` (`src/ralphd/engine/faults.py:88`) decides *whether this was
a failure* from process-level signals only:

```python
is_failure = (no_traffic_timeout or timed_out or interrupted
              or (exit_code is not None and exit_code != 0))
if not is_failure:
    return None            # exit 0 + "getaddrinfo EAI_AGAIN" lands here
```

`pi` reports endpoint failures **in-band and exits 0**. So the entire fault
apparatus — retry, refund, the instant-failure carve-out — is unreachable for
the failure shape that actually happens in production. `_INFRA_TEXT_RE` already
matches `EAI_AGAIN`; it is simply never consulted.

- An iteration that ends with a non-empty `error_message` is a failure
  regardless of `exit_code`. Reaching zero-token/no-traffic termination with an
  error recorded is not a success.
- Extend `_INFRA_TEXT_PATTERNS` to the signatures observed on this host and the
  ones any Bedrock/gateway deployment will produce: `Connection error`,
  `socket hang up`, `EPIPE`, `premature close`, `429`, `529`,
  `rate limit`/`ratelimit`, `throttl` (covers `ThrottlingException`),
  `Overloaded`/`overloaded_error`, `ModelStreamErrorException`,
  `ServiceUnavailable`, `internal server error`, `quota`, `capacity`.
  Keep it a single reviewable table with a one-line comment per family.
- The bare error `"aborted"` (seen on `deck-phase1` iteration 86) is
  ambiguous — it is also what an operator abort looks like. Classify it as
  infra **only** when the iteration produced no traffic and no
  operator-initiated abort/interrupt is recorded for it; otherwise leave it
  alone. Do not let an operator's abort become an infra retry loop.
- Record the classification where it can be audited after the fact: a
  `faultClass` field in `iterations/NNNN/meta.json` (`null` for success) and in
  the `iteration.end` event. The reason issue #11 took an incident plus a
  transcript dig to diagnose is that nothing recorded the engine's own verdict.
- Test bar: table-driven unit tests over `classify_fault` covering every
  signature family × {exit 0, exit nonzero} × {traffic, no traffic}; the exact
  `deck-phase1` shapes (`EAI_AGAIN`/`ECONNRESET`/`aborted` at exit 0, zero
  tokens) as named regression cases; the operator-abort case asserting it is
  *not* infra; and an e2e with a stub agent that errors in-band at exit 0,
  asserting an `infra_retry` event fires and `iterationsUsed` is refunded.

## B. Aggressive retry with an outage budget and an explicit degraded state (#5, #11)

Replace "3 attempts, first one a minute away, two phases" with "retry hard and
fast, for as long as the outage plausibly lasts, on every phase, and say so".

- **Fast escalating backoff**: default schedule `[2, 5, 15, 30, 60, 120, 300]`
  seconds, last value repeating (`infra_retry_backoff_max_s`, default 300). A
  30-second blip should cost ~seconds of delay, not a minute-plus.
- **Wall-clock outage budget instead of an attempt cap**: new
  `infra_outage_budget_s`, default **4 hours**, env
  `RALPHD_INFRA_OUTAGE_BUDGET_S`, `start` flag `--infra-outage-budget`. Retries
  continue while the *cumulative* wait for this fault episode is under budget;
  the episode resets on any successful iteration. `infra_retry_max` stays
  honoured when set explicitly (back-compat for tests and existing job.yaml)
  but defaults to unlimited-within-budget. Exhausting the budget fails with the
  same shape of `reason` as today, naming the total outage duration and the
  last error.
- **Every phase**, not two: `planning`, `worker`, `review`, `verify`,
  `reflect`. Where a phase already has its own retry (`verify`'s
  `MAX_VERIFY_ERROR_RETRIES`, `review`'s steering loop) the two must not
  double-count — an infra-classified failure is handled by the infra wrapper
  and must not consume the phase-local error budget or a task's
  `validationAttempts`. State the precedence in the code comment; the current
  comment asserting a policy that doesn't exist is what made #5 possible.
- **Instant-failure interplay — the important one.** Today an infra fault that
  is also *instant* (`< INSTANT_FAILURE_MAX_DURATION_S`, no traffic) returns
  immediately and is left to the streak guard. With aggressive retry, instant
  faults must be retried too (a refused connection is instant *and*
  transient) — but a missing API key is also instant, and must not become a
  four-hour hang. Resolve it explicitly: retry instant infra faults, but if
  `MAX_CONSECUTIVE_INSTANT_FAILURES` attempts fail instantly with **no traffic
  and a stable error signature**, stop retrying and fail fast with the existing
  broken-environment diagnosis. Transient faults vary and take time; a broken
  credential fails identically in 0.6s every time. Write that reasoning into
  the code.
- **The job deadline must not be eaten by an outage.** `self.deadline` is
  wall-clock; a 4-hour wait would silently consume half an 8-hour job.
  Accumulate `infraWaitTotalS` and extend `deadlineAt` by the waited time, emit
  an event when you do, and document it in `docs/api.md`. (If you conclude the
  opposite is right, argue it in the task notes — but it must be a decision,
  not an accident.)
- **Say it in the status contract.** `state` stays
  `starting|running|succeeded|failed|aborted` — do **not** add a state value,
  it would break every consumer's terminal-state logic, `watch` (#13) included.
  Instead add:

  ```json
  "health": "ok" | "degraded",
  "infraWait": {
    "since": "2026-08-18T09:14:02Z", "attempt": 4,
    "error": "getaddrinfo EAI_AGAIN aigw…", "phase": "worker",
    "nextAttemptAt": "2026-08-18T09:15:02Z",
    "waitedS": 52, "budgetS": 14400, "remainingS": 14348
  }
  ```

  `infraWait` is `null` whenever not waiting. Surface it in `ralphctl status`
  (a `degraded:` line with the countdown and the error), in the hub run-detail
  card (visually distinct from a healthy `running`), and in `ralphctl watch`'s
  event stream.
- Refunds and breakers keep today's guarantees: refunded iterations never count
  against the budget, and an infra episode never advances the no-progress
  stagnation guard or a task's failure bookkeeping.
- Test bar: a stub agent scripted to fail N times then succeed, asserting
  (a) retry count and backoff progression against a compressed schedule,
  (b) `iterationsUsed` unchanged across the episode, (c) approach count
  unchanged, (d) `health: degraded` + populated `infraWait` mid-wait and both
  cleared after recovery, (e) outage-budget exhaustion produces a terminal
  `reason` naming the duration, (f) the instant-failure fast-fail still fires
  for a stable zero-traffic error, (g) deadline extension arithmetic. Plus a
  reflect-specific case (below) and a verify-specific case asserting no
  double-counting.

## C. Manual retry-now during a wait (#5, #11)

An operator who has just fixed the gateway should not wait out a 300-second
backoff, and neither should an agent supervising ralphd.

- Engine: `POST /retry` wakes a waiting iteration immediately. Implement the
  wait as an interruptible `asyncio.Event` (same shape as `_pause`), not a bare
  `asyncio.sleep`. `409` when the run is not currently in an infra wait, with a
  message saying so. Note the naming trap: the engine's existing `POST /resume`
  is pause-resume, while `ralphctl resume` recreates the container — do not add
  to that confusion; `/retry` is about the backoff only.
- CLI: `ralphctl retry <run-id>`, `--json`, documented in `docs/cli.md`
  alongside `pause`/`unpause`. Exit codes consistent with the other control
  commands.
- A manual retry **resets the outage-budget clock** for the episode — the
  operator is asserting the endpoint is back. Say so in the docs and emit an
  event recording it.
- Retry-now does not unpause a paused run, and does not interact with steering.
- Hub: when `infraWait` is present, the run-detail card shows the countdown to
  `nextAttemptAt` and a **retry now** button posting to the same route via the
  UI server's proxy. Read-only when the run's API is unreachable.
- Test bar: engine test asserting a waiting iteration retries immediately on
  `POST /retry` (wall-clock assertion against a long backoff) and that the
  episode clock reset; `409` when not waiting; CLI test for both paths; browser
  e2e asserting the button appears only while degraded.

## D. Reflect must retry and must report (#5)

Covered mechanically by B, but it has its own failure mode and its own
acceptance criteria:

- Reflect is inside the retry wrapper (it is a single post-terminal iteration —
  no approach or task bookkeeping to collide with), and the
  `INFRA_RETRY_PHASES` comment matches reality afterwards.
- When the job has just ended on an infra-shaped failure, wait before the first
  reflect attempt instead of firing in the same second the breaker tripped.
- `_run_reflection` must **inspect its result**. On failure, record why: a
  `reflect` outcome in the run state and a `artifacts/reflection/FAILED.md`
  naming the error, so a missing reflection report is never silent.
- `ralphctl status` and the hub can both say "reflection failed: Connection
  error."
- Unchanged guarantees: reflect runs exactly once, strictly after the terminal
  state, and can never change `succeeded`/`failed`/`aborted`.
- Test bar: reflect fails infra-shaped → retried, then recorded as failed with
  the reason readable from both surfaces; reflect succeeds → report present, no
  failure recorded; terminal state unchanged in both.

## E. A run recorded running with no container must be visible everywhere (#8)

The check already exists — `doctor`'s `danglingRegistryEntries` — in the one
command that is global and report-only. The per-run surfaces all report the
zombie as healthy.

- `ralphctl repair <run-id>`: add the dangling-container condition to
  diagnosis, reusing `doctor`'s check rather than writing a second one. It must
  stop saying "no issues found", and must name the guarded fix. `--set-state`
  writes a `reason` explaining that the container vanished, into `status.json`
  and the repair audit event. `repair` still refuses to touch a run whose
  container is alive.
- `ralphctl status`: when the API is unreachable *and* the recorded state is
  non-terminal, say so on its own line rather than leaving the operator to join
  `state: running` with `live api: False`. Stop presenting a growing live
  `elapsed` for a run that has demonstrably stopped — label it as time since
  last update.
- Hub: this state must not render identically to a healthy `running` run;
  reuse the card's existing warning treatment.
- `ralphctl status` on an unreachable run prints `tasks: (none)` despite a
  25 KB `tasks.json`, because task counts are only computed by the engine's
  live `/status`. Compute them CLI-side in the on-disk fallback path.
- `doctor`'s suggested remedy and `repair`'s must agree (today `doctor` says
  try `resume`; for a run killed mid-verify, `repair --set-state` may be the
  honest first step — pick one story).
- Test bar: fixture run dir with `state: running` and no container → `repair`
  reports it and `--set-state aborted` writes state + reason + audit event;
  `status` shows the warning and non-empty task counts; hub browser test for
  the distinct rendering.

## F. Opt-in self-recovery of dead runs (#8 follow-on)

Detection (E) is the prerequisite; this is the recovery.

- New per-run setting `auto_resume`, **default OFF**, set by `ralphctl start
  --auto-resume` and defaultable via `ralphctl config set auto_resume true`.
  Persisted with the run's other start-time wiring so it survives a resume.
- `ralphctl doctor --fix` resumes every opted-in run it finds recorded
  non-terminal with no container. Document running it from cron/systemd; that
  is the intended deployment, and no new daemon process is in scope.
- Crash-loop guard: record `autoResume: {attempts, lastAt, maxAttempts}` in the
  run dir; escalating backoff between attempts; stop after the cap and leave a
  reason explaining that auto-recovery gave up. A run that dies instantly on
  resume must not be resurrected in a loop.
- Never auto-resume a run that reached a terminal state, or one the operator
  aborted/stopped deliberately — distinguish operator-initiated termination
  from a container that vanished. Getting this wrong resurrects runs someone
  killed on purpose.
- **Design the default so flipping it is a one-line change.** The intent is for
  `auto_resume` to default ON in a later version; keep the default in exactly
  one place, parameterise the tests over it, and note the planned flip in
  `docs/roadmap.md`'s deferred list.
- Test bar: opted-in dead run → `doctor --fix` resumes it (stub-docker,
  asserting the recorded `docker run` argv reproduces the original wiring);
  opted-out dead run → untouched, still reported; terminal run → untouched;
  crash-loop cap reached → gives up with a reason; operator-aborted run →
  untouched.

## G. `watch` must not close on a historical terminal marker (#13)

`ralphctl watch` replays `events.jsonl` and closes at the **first** terminal
state event it sees. On a resumed run that marker is history, so the documented
agent completion-wait —

```
ralphctl watch <id> --json | jq -c 'select(.type=="state")'
```

— returns the stale `aborted` and exits 0 while the job is alive. It fails
silently, successfully, and precisely after a crash recovery or budget top-up,
which is when supervision matters most. Observed on
`est6534-impl-phase2-sessions`: abort marker at event 242, engine appending
243–284+, two successive followers both quitting at 242 mid-iteration-58 while
`status` said `running` throughout.

- A terminal-state event ends the stream only if it is the log's **last** event
  *and* the engine is not live. Reconcile against live state rather than
  trusting a replayed marker.
- Emit an explicit `state: running` (or `resumed`) event on resume so a
  historical terminal marker can never be the log's final word, and have the
  follower track the latest state rather than halting on the first terminal
  one.
- Check whether `ralphctl logs -f` (a different route, `GET /logs`) shares the
  behaviour; fix it in the same pass if so.
- Update `docs/cli.md`'s completion-wait snippet — it is the contract agents
  follow.
- Test bar: fixture with a terminal marker mid-log and later events → follower
  streams past it and blocks until the real terminus; live-run and
  already-finished-run cases both unchanged; a regression test named for the
  resumed-run scenario.

## H. The agent must not be able to delete its own container (#7)

`ralphctl start` labels the job container `ralphd.run=<run-id>`, and
`loop.py:219` tells the agent to label every sibling with the same label. So
the documented cleanup filter selects the container the agent is running
inside. Prompt guidance alone already failed once here (the iteration-103
`pkill` incident) and failed again on `deck-phase1`.

- Add `ralphd.role=job` to the job container and have the documented sibling
  pattern apply `ralphd.role=sibling`, making the safe idiom expressible:
  `--filter label=ralphd.run=$RALPHD_RUN_ID --filter label=ralphd.role=sibling`.
  `_reap_siblings()` keeps its run-id-only filter — `ralphctl stop`/`rm`
  deliberately want the job container too.
- Tell the agent the sharp edge exists in the same prompt block that hands it
  the label: the job container carries it, removing by it kills the run
  mid-iteration and loses the work, reaping is `ralphctl`'s job, and here is the
  sibling-only form. Rule plus the why — unexplained rules read as optional.
- Export `RALPHD_SELF_CONTAINER_ID` into the container so guidance can name the
  one id never to touch.
- Same rule in every duplicate: `loop.py`'s `_docker_siblings_note`,
  `examples/skills/toolchain-sibling/SKILL.md`, `docs/architecture.md:951/975`,
  `docs/cli.md:157`.
- Test bar: the documented sibling-cleanup command, run against a fixture with
  a labelled job container plus labelled siblings, leaves the job container
  alive; `ralphctl stop`/`rm` still reap everything (unchanged); a test
  asserting the prompt carries the prohibition.

## I. Logs must survive the container (#6)

`GET /logs` is itself only a read-side merge over the run dir
(`api.py:_merge_logs` walking `iterations/*/meta.json` + `output.jsonl`), and
that dir is host-mounted and complete for every dead run — the project's stated
"history outlives the container" property. Yet the hub's log tail is
proxy-only, `ralphctl logs` dies on connection-refused, and `status` on the
same run degrades gracefully. Every failed run investigated so far had to be
read out of `output.jsonl` by hand for this reason.

- Extract the merge + boundary-line synthesis into a module both the engine and
  the CLI import. The engine keeps its live `follow` behaviour on top.
- Hub: `rendered_log_lines()` falls back to the on-disk merge, returning
  `live: false` so the UI can label it "on-disk snapshot" (wording the detail
  card already uses for status).
- CLI: `ralphctl logs` on an unreachable run reads the same merge, exits 0, and
  notes on stderr that this is a snapshot. `--follow` prints the snapshot and
  exits cleanly with a notice. `--raw` keeps its 1:1 wire contract from the
  same merge.
- **Redaction is a real difference and must be a stated decision**: the engine
  re-scrubs at serve time on top of the write-time scrub; a host-side reader
  has no redaction map. Either accept it (on-disk transcripts are already
  scrubbed at write time) or persist enough of the map with the run to re-apply
  the second pass. Document the choice in `docs/architecture.md`'s redaction
  section.
- Test bar: hub endpoint test for the dead-run fallback; CLI test asserting
  non-empty output and exit 0 for an unreachable run; a test that live and
  on-disk paths render identical lines for the same fixture; empty
  `iterations/` renders an explicit "(no transcript yet)" on both surfaces.

# Phase 2 — operator surfaces and quality of life

Start only once Phase 1 is committed and green. Ordered by how much each one
costs an operator today.

## J. Top up the iteration budget in flight (#3)

`PATCH /config/budget` plus `ralphctl budget <run-id> +N` (and an absolute
form), applied without restarting the container. Bounds and validation
(never below `iterationsUsed`), an audit event, and the new value visible in
`status`/hub immediately. This is resilience-adjacent: today the only way to
grant a finished-but-unreviewed job a review slot is a full `resume`.
Test bar: API accept/reject cases, CLI round-trip, an e2e where a job about to
exhaust its budget is topped up mid-flight and continues.

## K. Absolute timestamps in the iteration timeline, logs, and status (#4)

Hub timeline and `ralphctl logs`/`status` show absolute local-time timestamps,
not just relative durations. One shared formatter, used by both surfaces, with
the raw ISO value kept in the payload (K and M interact — see M's note).

## L. Unknown cost must not render as `$0.0000` (#10)

ralphd sums the provider's `usage.cost.total` and `runner.py:207`'s `or 0`
turns "no pricing available" into a confident zero. On this host that means
four runs — up to 102.4M tokens — read as free, and
`--model-strategy cost-optimized` has an all-zero cost side to optimise
against.

- An iteration with `totalTokens > 0` whose provider reported no pricing
  records cost as **unknown**, not `0`; a run total that mixes priced and
  unpriced iterations is labelled **partial** rather than silently summing a
  subset. An iteration with no traffic keeps today's behaviour.
- Hub, `ralphctl status`, the `logs` footer and the TUI cost gauge all render
  unknown as unavailable. A fully-priced run (`selfdev-roadmap-2`, `$91.66`) is
  byte-identical to today.
- Optional and worth it here: a host-side `pricing:` map keyed by model id
  (per-million rates + alias→canonical mapping for gateway names), applied when
  the provider reports none and marked as *derived* wherever displayed. It is
  the only route to real numbers for the `aigw-openai/*` aliases, which no
  upstream pricing table can ever know.
- `docs/api.md`'s usage contract gains the unknown/partial case and what the
  `byPhase`/`byApproach` summation invariant means when buckets are unknown.
- Also investigate the one anomaly: `eu.anthropic.claude-opus-5` was priced in
  `est6534-opus5-smoke` (06:39) and unpriced in `est6534-impl-phase2-sessions`
  (08:13) on the same image. If pricing is fetched at runtime and falls back to
  zeros, *any* run's cost can be understated — at minimum record which
  iterations were priced.

## M. Sortable, newest-first run list (#9)

Hub run list sorts on click (all seven columns, reversible, indicated), and
defaults to `STARTED` descending instead of run-id alphabetical. Three traps:
`ITERATIONS` must sort numerically on `iterationsUsed` (the cell is `17/250`),
`STATE`/`VERDICT` must sort in lifecycle order rather than alphabetically, and
**sort state must live outside the DOM** because `load()` rebuilds the table
every 4s — otherwise the table snaps back mid-read. Sort on the raw `startedAt`
from the payload, not the rendered cell (K changes that text). CLI parity:
`ralphctl runs` defaults newest-first too, with `--sort`/`--reverse` covering
the same keys, `--json` ordered identically, composing with `--state`.

## N. PRD and task detail in the hub (#1, #2)

A run's PRD opens in a dialog from the run-detail page (#1); tasks are
clickable and open a task-detail dialog (#2). Both render agent-authored text
with `textContent` only — the task-014 rendering discipline in `app.js` — never
`innerHTML`. Serve the PRD from the existing `GET /prd` with an on-disk
fallback for dead runs, consistent with I.

## Cross-cutting requirements

- **Docs sync, in the same commit as the behaviour**: `docs/api.md` (`health`,

  unknown/partial), `docs/cli.md` (`retry`, `budget`, `runs --sort`,
  `--auto-resume`, `--infra-outage-budget`, the fixed completion-wait snippet),

  plus the `auto_resume` default-flip note).
- **Configuration discipline**: every new knob has a `JobConfig` default, a
  `RALPHD_*` env override, and appears in `GET /config`'s effective view — the
  existing pattern. Compressed schedules must be settable so tests never sleep
  for real.
- **No silent behaviour changes to a healthy run.** A run that never hits a
  fault must behave exactly as it does today, and the existing suite must stay
  green without modification except where a documented contract changed (state
  fields, default run ordering).
- **Final artifact**: `artifacts/reports/issue-traceability.md` mapping each of
  #1–#11 and #13 to its requirement, task, commit, and tests. Do not close the
  issues.

## Non-goals

- No new daemon or supervisor process. Self-recovery rides on
  `ralphctl doctor --fix` invoked by the operator's scheduler.

- No new `state` value. `health`/`infraWait` carry the degraded case
